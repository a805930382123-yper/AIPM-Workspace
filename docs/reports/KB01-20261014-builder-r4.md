## 长文定位诊断与实现

现有 `locateEvidence` 接受当前chunk内精确有效的全局UTF-16 start/end，或唯一匹配的原文quote；无效位置提示会退回唯一匹配。当前长文chunk2的quote在同一chunk内出现两次，服务端缺少能判断模型所指实例的确定信息，故正确以 `LLM_EVIDENCE_AMBIGUOUS` 失败。前轮 `LLM_EVIDENCE_UNKNOWN_ID` 是逐页证据ID引用不闭环的独立输出错误。单纯要求更准确quote/offset无法建立可验证的位置映射。

按主Agent确认的locator v2实施：每个chunk连续切成≤512 UTF-16 code units的锚点，优先句/段边界，最多256项并校验覆盖、顺序、精确Raw切片、唯一ID和代理对边界。目录只含服务端生成ID和对应原文文本，不给模型偏移。模型v2必须提供顶层 `evidence_format_version: 2`，每条 `source_evidence` 严格只含 `id`、`locatorId`；v2不接受模型给出的rawId、quote或offset。未知、跨chunk及格式混用均拒绝。

v2先用独立严格的provider schema验证，再以当前Raw ID绑定来源，并从当前chunk locator派生规范化 `rawId/quote/start/end`，随后继续执行原有完整提取schema、页内引用、原文切片和chunk检查。持久化草稿格式、既有提取schema文件和文档级merge输入没有变化；merge只见规范化Raw证据，不透传chunk locator。无 `evidence_format_version` 的旧provider quote格式仍完整通过旧schema校验，旧quote歧义依旧 `LLM_EVIDENCE_AMBIGUOUS` fail closed。请求仍保留原 `<<<...>>>` Raw正文块；调用数、并发、timeout、重试与预算均未改。

首轮locator实现后，主Agent静态检查发现共享提取规则中固定的“两字段顶层”和`quote/rawId`指令仍与v2相冲突。已通过按原规则全文精确命中的命名覆盖构造chunk-v2 system prompt；只有这两条改为v2语义，其余原安全规则完整保留，规则漂移导致覆盖目标找不到时明确失败。parser继续兼容旧quote格式，但请求不再鼓励模型运行时回退。`rulesVersion`现在显式包含`locator-v2`并纳入版本哈希。document merge独立采用document-only专用覆盖，明确不输出/修改source_evidence，且system prompt不含locator v2。Raw正文与原本地JSON merge输入合同保留。

独立静态复核又发现v2从Raw派生quote后没有重新扫已知Key。现于归一化完整provider结果上保留原解析前扫描，并追加一次 `assertNoKnownSecret`；chunk请求显式提供稳定格式 `当前 Raw ID：<uuid>`，只作上下文且明确不输出到v2 evidence。fake helper（含repair3流程）改从该字段取ID。新增安全回归让provider只返回不含Key的locator ID，locator指向含虚构已知 `test-key` 的Raw片段；实际结果为 `LLM_OUTPUT_CONTAINS_SECRET`，处理状态失败、无草稿、无正式Wiki和日志。

主Agent独立复现了重叠块相同证据的聚合失败：两块对同一Raw全局区间报告相同ID/来源/位置/引文时，之前只按对象引用去重，导致重复ID。现在按 `id + rawId + start + end + quote` 判定相同来源并折叠重复证据；`chunkIndex`不纳入身份，因为同一全局Raw范围会由两个chunk分别报告。相同ID但来源/区间/引文不同仍按chunk后缀重命名，事实引用随ID同步。新增双chunk同ID同全局范围回归，并实际执行文档汇总校验。

主Agent另复现确认期间的选择竞态。当前确认、保存、决策、候选查询等异步操作期间，所有可变审核字段、页面选择框和批量选择控件统一禁用；Raw阅读和导航仍可用。新增挂起候选刷新回归，确认其间的选中项、PATCH快照与最终selectedPageIds一致。

## R4后续小修：受限启用 GLM JSON mode

主Agent独立单变量诊断在原失败chunk请求上只增加`response_format: { type: 'json_object' }`，得到HTTP 200、`finish_reason=stop`，结果通过v2完整schema并返回3条建议（一次样本约15.493秒）。我据此在Provider既有的`purpose === 'knowledge'` + 精确host（`open.bigmodel.cn`或`api.z.ai`）+ 精确模型（`glm-5.3-flash`）low-reasoning分支中附加同一JSON mode字段。所有其它purpose/host/model的wire body保持原样；温度、top_p、timeout、调用数、重试、schema与错误门禁未变。

官方依据：Z.AI [Structured Output文档](https://docs.z.ai/guides/capabilities/struct-output)将`response_format: { type: 'json_object' }`定义为启用JSON mode的参数，并示例仍由调用方验证schema；[GLM-5.3-Flash模型页](https://docs.z.ai/guides/vlm/glm-5.3-flash)列出该模型支持structured output。该参数只提供格式约束依据，不代表模型会满足本产品领域schema、证据引用规则或事实准确性；应用既有严格校验仍是最终门禁。单次成功样本仅支持继续受控复验，不足以证明长文、各chunk或真实质量稳定。

`tests/provider-knowledge-reasoning.test.ts`的内存wire用例现断言精确批准范围同时附加low reasoning和JSON mode；伪造host、其它模型和无knowledge purpose仍不带两字段。隔离副本关联测试`provider-knowledge-reasoning.test.ts provider-config.test.ts llm.test.ts llm-flow.test.ts`：**41/41 PASS**；副本`npm run build`：PASS，仍有既有bundle >500 kB提示。本次代码与测试改动仅为`services/llm/provider.ts`、`tests/provider-knowledge-reasoning.test.ts`及本报告；未执行Provider调用。
