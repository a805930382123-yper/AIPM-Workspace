## 最小实现与文件范围

[精确范围与前后SHA](KB02-SR01-R2-20261021-scope.json)：只改3个既有产品文件，新增1个窄助手；默认测试只新增1个文件7项，原测试未改。

| 文件 | 行为与边界 |
|---|---|
| services/storage/job-file-access.ts（新增） | 只匹配`state/extraction-jobs/*.json`。按规范化绝对文件路径协调，Windows大小写归一；同文件队列共享于多store实例，其他job/其他目录独立。空闲队列自动删除。 |
| services/storage/files.ts | 对job文件的readJsonRecord/readJsonFile、扫描的完整open→read→close、完整atomic临时写入→rename→错误清理使用共同I/O队列。其他目录直接执行原操作。原rename最多6次、原退避、错误类型、字节/文件扫描预算保持。 |
| services/llm/jobs.ts | insert/update另用同job的复合变更队列，跨实例读后更新不会互相覆盖字段。内部get及atomic写入使用独立I/O队列，因此无同锁递归；不修改任务执行/恢复/预算算法、startStateHash或缺cp规则。 |
| services/storage/recovery.ts | RecoveryRegistry对job记录的读句柄也参加同一I/O协调，直到close完成才释放；原扫描统计、坏记录、溢出和诊断契约保留。 |

I/O协调与复合变更协调分离：读者不获取复合变更队列，变更先排复合队列再做单次I/O，不引入相互反向等待。正常轮询允许在完整写入前或后读取完整记录，不能在原子替换时持有同文件读句柄。不同job之间没有全目录锁。

此处是本进程按绝对路径的资源协调，不声称阻止其他进程/外部占用，也不证明历史两次call-count-job异常只有这一原因。没有扩大文件重试、模型超时或调用额度，未吞错误、强制completed或自动补模型请求。

## 新回归与原版对照

新增`tests/kb02-job-file-access.test.ts`七项，使用真实job store和文件句柄，未靠玩具状态机：

1. 持有get读句柄时，另一store的update不能开始rename，其他job仍可完成。
2. 同样约束另一store的insert。
3. atomic rename尚未完成时，get/list/通用JSON读/独立恢复扫描都不能打开同目标；释放后读到完整新记录。
4. list必须等待真实读句柄close完成后才允许写入。
5. RecoveryRegistry同样覆盖完整close生命周期。
6. 多实例并发更新保留独立字段；坏JSON读取或持续rename失败后释放队列；故障在时原字节保留，原6次失败可见，解除后可写。
