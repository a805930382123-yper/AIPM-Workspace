# 开发协作规则

## 通用 Agent Router 现行规则（2026-10-27）

本项目采用 [agent-router](../.agents/skills/agent-router/SKILL.md) 的通用调度流程。该 Skill 是当前评分、角色映射、施工—独立验收及范围内自动返修规则的维护位置；模型及推理参数见其 [角色配置](../.agents/skills/agent-router/references/roles.md)。本节覆盖下方旧版本的模型分工、评分路由、主 Agent 必须亲自验收及逐轮返修需再次确认的冲突安排，不改写历史实际模型和验收记录。

当前默认：0–1 分为 A 轻量（Astra 规划、Luna High 施工、Sol High 独立验收），2–4 分为 A 标准（Astra 规划、Terra High 施工、Sol High 独立验收；3–4 分先审计划），5–8 分为 B（Astra 规划、Sol High 施工、Astra 独立验收）。重大风险直接 B，核心需求不清先澄清，同核心缺陷修后再失败先诊断；具体评分及调用边界以 Skill 为准。

本项目继续从 status.md 及其引用定位当前任务与最新验收，沿用 agent-control.md、acceptance.md 和既有报告，不新建平行台账。下方只读预检、项目数据不变量、真实调用预算、双层验收和证据要求继续适用。已有有效方案复用；新调度按当前风险评分，当前已授权批次不因规则更新自动重开或重置预算。

范围内缺陷按 Skill 自动返修并独立复验；范围、标准、预算变化或需要新增授权时交用户决定。每批汇报后仍等待用户确认，不自动启动下一批。提交推送仅按 AGENTS.md 的有效项目授权执行，通用 Skill 不给其他项目默认同步权限。规则配置更新本身不启动产品施工，也不证明模型已经实际调用。

## 项目状态预检

入口为项目根 [AGENTS.md](../AGENTS.md)。用户明确要求“检查项目状态”“切换电脑后恢复进度”等任务时，主 Agent 执行此预检；它是现有 Agent-Router 的只读检查入口，不改变下方 A/B 评分、Agent 分工、施工自查、主 Agent 独立验收和升级门禁。

### 检查顺序与证据

1. 先定位当前仓库实际生效的规则及其引用，沿用现有结构。本项目从 AGENTS.md 进入本文件，状态入口为 [status.md](status.md)，总控依据为 [agent-control.md](agent-control.md)；按状态链接读取当前任务卡和最新验收报告，不凭文件名或修改时间猜测最新结论，不另建台账。
2. 读取仓库路径、分支、完整 HEAD、暂存/未暂存/未跟踪修改及远端地址。可以使用 `git status --short`、`git branch --show-current`、`git rev-parse HEAD`；实时远端核验使用只读 `git ls-remote origin refs/heads/<当前分支>`，记录实际返回与检查时间。禁止用 fetch 更新本地状态来完成预检。未执行、失败或远端分支无法对应时，明确写“远端状态未验证”；本地 origin 引用和 ahead/behind 仅是缓存。即使 HEAD 与实时远端一致，也分别披露未提交修改；不能推定其他设备没有工作，无法确认时写“其他设备本地状态未知”。
3. 从最新状态和验收证据识别阶段、当前批次、上轮完成内容、未解决问题、阻塞、预算门禁及待确认事项；分别报告“本轮施工范围内缺陷修复结果”和“批次整体验收结果”，不以完成百分比或局部通过替代批次门槛。
4. 核对报告中的提交/冻结标识是否在当前可见历史中，必要时只读比较相关代码差异或文件摘要，检查状态与代码、报告是否一致。历史测试必须标注“历史报告结果”及对应代码版本、命令/证据路径；未经本机本轮运行不得称为本次测试通过。发现冲突并列证据、说明尚不能确定的结论，不自动选择一份、改写记录或修复代码。
5. 只读检查本设备后续协作所需的规则入口、任务引用、可见 Agent 角色/模型配置及工具能力；仅查看必要配置字段，不输出凭证。分别标注“文件存在”“当前会话已暴露配置/能力”“本机本轮实际调用验证”；前两者不等于实际调用成功，历史调用也不等于本设备当前可用。默认不为探测配置而派发子 Agent。配置缺失、主 Agent 要求与可见默认模型不一致、模型调用能力未验证时如实列出；不安装、不修改全局或项目配置，不声称另一台电脑已验证。
6. 给出下一步建议、暂定 A/B 模式及其现有依据，说明能否继续和待确认事项。此处仅建议，不创建施工任务、不派发 Agent；若需要额外授权，先报告具体操作及原因。

### 只读边界与汇报

预检只读取和汇报，原则上不调用子 Agent、不运行全量测试；不启动产品服务或真实模型测试，不修改项目状态/验收结论，不自动同步或修复，不拉取、合并、重置、清理、提交或推送。该边界优先于日常“任务修改完成后提交同步”约定；即使检测到本地领先、未提交文件或设备配置缺失，也仅报告。若另获明确的修复/配置/同步授权，作为后续任务按对应规则执行，不能混称只读预检。若本次任务先授权修改规则再要求预检，先完成必要规则增量，随后只读检查并披露这些未提交修改，不借预检触发提交同步。

使用下列六项汇报，关键结论附文件路径、提交或实际检查结果：

- 本机版本与同步核验情况。
- 当前阶段和批次。
- 上轮施工结果与批次整体验收结果，分别说明。
- 剩余问题和阻塞。
- 下一步建议及暂定协作模式。
- 当前能否继续，以及尚待确认的事项。

汇报中区分本次实查、历史证据、未验证项；跨设备验证尚未执行时明确保留。汇报后停止，不启动施工，也不新增预检状态台账。

## 最新主Agent—子Agent施工验收闭环（2026-10-22）

用户指定Astra担任主Agent，负责问题审查、返修方案、任务派发、独立验收及下一步计划。已有Astra确认的问题与方案直接使用，不重复规划；已确认A/B模式沿用。本轮B模式施工角色为 `sol_repair`（GPT-6.1 Sol High）。实际角色/模型以工具创建或宿主设置为准，文档不宣称已切换模型，也不更改历史Agent身份。

施工者按方案修改、逐项自查、执行必要测试、自行修复局部问题并提交施工与自查报告。主Agent必须等待施工交接及停写，再独立检查实际代码差异、原验收标准及测试证据，不仅凭施工自查裁决；施工者不得自签验收通过。历史重复核心失败升级规则仍适用。

验收结论统一为“通过 / 未通过 / 阻塞待验证”；明知存在产品失败时不得以阻塞掩盖失败，必选实测缺失不得通过。验收后更新agent-control与status，汇报施工内容、自查结果、独立验收及证据、遗留问题风险、项目阶段与批次状态、下一步计划和建议A/B模式。未通过给明确返修建议，通过给下一批计划。**汇报后等待用户确认，不自动启动下一批次施工。** 此约定优先于下方旧调度流程。

## 当前总控规则（2026-10-22 起）

A 模式施工配置已按用户 2026-10-27 指令更新；用户指定按批次四维风险评分动态选择A/B模式，覆盖下方2026-10-15固定分工与历史升级约定。每批执行前读取[agent-control.md](agent-control.md)，依据里程碑与验收门槛识别阶段，列出需求明确度、模块耦合度、修改风险、历史失败各0–2分及证据。0–2分A：GPT-6.1 Terra High（`gpt-6.1-terra` / `high`）施工、6.1 Sol独立审查；3–4分优先A并由Sol先审计划；5–8分B：6.1 Sol施工、Astra独立审查。重大跨模块数据完整性、安全、升级兼容风险可直接B；关键需求歧义先由Astra澄清重规划。

同一核心缺陷修复后再次失败时暂停重试，由Sol诊断根因后决定升级或Astra重规划。独立审查核对原始标准、实际差异、必要测试及回归，不得自签施工结果。每批验收后更新总控记录并重新评分；未过必要门禁不得推进依赖批次。每次调度报告阶段依据、目标、评分、模式、施工与审查Agent、门槛、升级条件和状态更新。具体执行范围仍以用户最新授权及status为准。

## 历史用户指定分工（2026-10-15，已由上方动态规则覆盖）

用户最新要求：后续返修由 **GPT-6.1 Sol High（gpt-6.1-sol / high）施工**；用户将在新窗口指定 **GPT-6 Astra 中（gpt-6-astra / medium）做独立批次审查**。本约定覆盖旧任务卡、返修报告中的 Luna 施工、主 Agent 验收及自动升级安排。保留历史报告原文作为当时证据。

当前聊天负责范围、交接和施工协调；以指定模型创建 Sol 施工子 Agent。Sol 完成修复、必要回归和构建，提供逐项返修映射、命令结果、文件指纹和遗留项后停止产品/tests 写入。本聊天不自动启动 Astra 审查、不以施工自测签批次 PASS；交付状态为“施工完成、待独立审查”或如实记录未完成。新窗口审查者依据冻结实物独立裁决 PASS/FAIL/BLOCKED。模型由实际创建参数或用户窗口设置决定，修改文档不等于修改当前宿主模型。

每次只处理当前授权批次，后续批次仍受批次门禁约束。真实 Provider 验收预算按原账本累计，施工仅使用隔离虚构数据和本地 fake，不消耗真实预算；真实调用及实际浏览器质量验收留给独立审查阶段。不得因换施工模型重置预算。

## 固定职责（历史安排）

| 角色 | 指定模型/推理强度 | 责任 |
|---|---|---|
| 主 Agent | GPT-6 Astra / Ultra | 工程接口、批次任务卡、验收标准、范围裁决、升级调度和最终汇报 |
| builder | `gpt-6-luna` / `high` | 只施工当前批次，执行必要检查，修复验收缺陷 |
| acceptance_monitor | `gpt-6.1-sol` / `high` | 独立验收与本批进度监控，复核证据，判断 PASS/FAIL/BLOCKED |

本轮两个子 Agent 已通过指定 model/reasoning_effort 创建。主 Agent 模型由当前聊天宿主设置决定，文档声明不是模型切换；不声称通过仓库文件修改了宿主模型。

## 批次闭环

1. 主 Agent 冻结当前任务卡的输入、交付物、接口、范围、验收 ID、文件所有权。
2. builder 读取 AGENTS、当前任务卡、相关代码；仅在需要时查询完整需求对应章节。施工时 monitor 可准备 fixtures/验收脚本，避免并发写同一文件。
3. builder 交接：变更文件、已跑命令及结果、未完成项、风险。主 Agent 验证交付范围。
4. monitor 对实际交付版本验收，记录命令/操作、预期、实际、证据路径和状态。代码静态检查不能替代真实操作；fake 不能冒充真实 LLM。
5. FAIL 返回最小复现与最小修复卡；修复后只重测受影响断言及关键回归。BLOCKED 单列外部条件。
6. 所有本批必选项 PASS 后，主 Agent 更新状态。下一批需处于用户最新授权范围，具体见 docs/status.md；用户要求验收后停止时不自动进入下一批。

用户看得到真实进展；监控只在当前施工回合中进行，关注超范围改动、反复失败、缺失证据和数据不变量，不创建后台常驻轮询或计划任务。

## 历史默认模型升级顺序（已由当前用户指定分工覆盖）

**GPT-6 Luna High → GPT-6.1 Sol High → GPT-6 Astra Medium（中）**。

- 同一问题两次有证据的修复仍未通过，或有明确能力瓶颈，提交升级；证据包含复现、预期/实际、尝试与结果、涉及文件和待解决点。
- 环境限制、网络故障、无 API Key、未明确业务取舍属于外部阻塞；先定位并报告，升级模型不能替代缺失条件。
- 主 Agent 使用更高一级模型新建临时施工子 Agent，只传失败任务卡与最小上下文，停止旧施工者对该范围的写入。工具无法原地改模型，不能只在提示词里“扮演”更高模型。
- 施工升级到 Sol 时，原 Sol monitor 继续独立验收，不让同一实例同时修复和自我验收。临时施工 Agent 任务结束即退出；常规两角色分工保留。
- monitor 自身遇到能力瓶颈时交主 Agent 裁决，可用 Astra Medium 临时复核；升级施工不能同时消耗验收独立性。
- Astra Medium 仍无法完成：主 Agent记录 blocker、证据和可行选项，不无限循环、不降验收门槛。
- 升级仅覆盖当前难点，完成后普通任务回到 Luna High。主 Agent 的 Ultra 是规划职责配置，不作为施工自动升级的下一档。

## 控制 token 与耗时

完整 PRD 只存一份；常驻规则短小，按任务卡增量加载。一次一个可演示闭环，建议 3–6 个相关交付点；超范围拆批，不在一个任务里重读/重做全产品。

每次报告只列变更、证据、问题和下一步。已有检查通过且代码未变时复用证据；整套回归留到关键集成点。报告实测耗时；平台未暴露子 Agent token 计量时写“不可得”，不估造成真实计费数，也不承诺一定省多少。

## 任务卡/交接格式

任务卡：批次目标 / 必做与排除 / 依赖与接口 / 文件所有权 / 验收 ID / 交付命令与操作 / 结束条件。

验收报告：交付版本或文件指纹 / 检查项与证据 / PASS、FAIL、BLOCKED、NOT_RUN / 缺陷与复现 / 回归影响 / 可否进入下一批。
