# SR01 R1 正常存储写入失败：有界诊断

2026-10-21（北京时间）。按用户要求读取 [独立验收](KB02-SR01-R1-AUDIT-20261021-acceptance.md) 和 [最小诊断与复验卡](KB02-SR01-R1-AUDIT-20261021-repair.md)，本轮只诊断，不修改产品或默认测试。F-SR01-01/02已受控关闭的结论保留；**SR01整体FAIL不变**，没有执行根因处置后的完整签收。

## 结论与置信范围

**已证实当前宿主存在“本进程同文件读取与原子替换重叠，可以导致原生rename EPERM并耗尽原重试”的触发机制。** 原预算测试的真实失败现场也记录到这一重叠，应用内读写竞争应作为最小修复的优先方向。不能将问题仅归为Node24.20、杀毒、索引器或权限设置，也不能承诺串行化就消除所有外部占用。

本轮没有重现旧独立完整suite两次相同的call-count-job自然失败；保留到的是另一次**failed-job**自然失败，以及明确标为synthetic的call-count-job语义验证。它们不能强行合并为旧两次故障的唯一系统根因。无永久句柄泄漏的实证；所有trace退出时观测到的活动读操作/显式句柄均为0。

## 已确认的代码窗口

`services/llm/jobs.ts`中ExtractionJobStore只有update使用其SerialQueue；get直接readJsonRecord/readFile，list直接scanJsonRecords/open，insert直接原子写。`ExtractionRunner.readJob()`在后台运行时调用jobs.get；预算fixture每10ms轮询readJob，因此轮询可以与beforeCall的job次数写入、进度或终态写入重叠。串行化写者不等于串行化该文件的读写。

真实产品还有HTTP job读取和`services/storage/recovery.ts`的RecoveryRegistry独立扫描jobs目录。未来最小修复需核对这些读路径，不能只在测试里减慢轮询，也不能只改一个store实例而遗漏同root的其他读取者。当前证据不要求扩大共享rename重试，更不涉及模型预算公式。

## 实验与证据

所有实验位于逐字节隔离副本或可丢弃临时目录，未使用正式workspace/config。原产品、默认测试和原断言不变。观测只包裹原I/O一次调用、记录并原样重抛，没有加重试/扩大超时/净化返回。

### 1. 两版本的最小读写对照

[执行记录](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-11-26.651Z-run.json)，[Node24.20探针](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-11-26.651Z-events/probe-system.json)，[Node24.19探针](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-11-26.651Z-events/probe-bundle.json)。使用实际writeJsonAtomic和原有最多6次rename尝试，不改其策略。每个普通场景至多80次写；连续读取场景累计4次写失败即停止。

| 场景 | Node24.20.0 | Node24.19.0 |
|---|---|---|
| 只写，无并发读取 | 80/80写入，原生错误0 | 80/80写入，原生错误0 |
| 同文件串行读完再写 | 80/80写入，原生错误0 | 80/80写入，原生错误0 |
| 每10ms轮询读取，与写入并发 | 77成功/3失败，30次原生EPERM | 80成功/0失败，3次原生EPERM、在原重试内恢复 |
| 连续读取，与写入并发 | 8成功/4失败后停止，39次原生错误 | 41成功/4失败后停止，73次原生错误 |
| 本进程明确持有一个读句柄 | 1次写入失败，6次原生EPERM | 1次写入失败，6次原生EPERM |

**关闭本进程读句柄/停止读者后，每个场景追加的3次写入两版本全部成功。** 这是本机上的受控因果对照，不是所有Windows环境或实际项目已修复的证明。没有停系统服务、改ACL、下载运行时或取消安全检查。

### 2. 原预算测试观测与原件保留

单进程原两项：[执行记录](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-03-10.848Z-run.json)，2/2通过但有10次原生rename EPERM，不能因测试通过称当时无存储竞争。

一次有界并发观测：每版本4进程、每进程原2项测试，各fixture独立；[执行记录](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-13-32.026Z-run.json)。系统24.20合计7/8项通过、1失败，bundle24.19合计8/8通过。该负载用于捕获现场，不作为完整默认suite签收，未反复跑完整suite刷绿。

自然失败为旧`last available planning call...`在第三次调用已返回覆盖失败后，**failed-job**状态保存失败：job仍running/callCount3，cp attempts3/成功块1/原覆盖诊断存在，Raw failed，Provider实际3次。保留了磁盘job/cp/raw-state/Raw正文原字节及各文件SHA256，[现场清单](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-13-32.026Z-events/budget-system-1-28352-fa2c7f20-d3ae-43ef-95b6-b86885c5e377/snapshot.json)，[原始时序](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-13-32.026Z-events/budget-system-1-28352.json)。

该同一临时文件的6次rename全部原生EPERM，跨度约631.646ms（原300ms退避之外还包含I/O和调度耗时）；其中5次进入rename时，观测到本进程有针对同一目标的未完成readFile。另1次没有观测到活动读者，因此不能把每次拒绝都唯一归给应用或据此排除外部占用。[按临时文件分组的分析](KB02-SR01-IO-DIAG-20261021-analysis.json)保留每次读者数量和前后读取时序。

不含人工注入的9次原测试进程（1次单进程＋8次并发）共71次原生rename错误，其中42次进入时有同文件活动读者；其余29次不支持直接定位占用者。probe的明确持有句柄实验比单纯相关性更能支持应用内竞争这一方向，但仍不能追溯重建旧审核失败的未保存句柄状态。

### 3. call-count-job仅保存恢复语义

[执行记录](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-03-47.665Z-run.json)，[语义断言结果](KB02-SR01-IO-DIAG-20261021-2026-10-21T10-03-47.665Z-events/semantics-result.json)。只在隔离fixture针对running/callCount3的job真实atomic rename人工注入6次EPERM；这不是自然故障根因证据。

断言全部通过：

- 故障停止时job次数2、cp次数3、成功块1、实际Provider2次；cp无诊断，不编造已经清掉的覆盖诊断。
- 解除故障后显式reconcileStorage仅保存，job提升到已持久化cp的次数3，cp仍3、成功块不变、Provider仍2；不返还已保留的尝试次数、不补发第三次请求。
- 重复仅保存字节不变；缺覆盖诊断时planningRetry拒绝且零调用。
- 用户显式普通继续后沿同job执行，cp次数4、实际Provider3次，只有这次显式操作新增1次请求并完成草稿。

因此，检查点次数高于实际外发次数是此失败分支的保守尝试记账，不能将它改成减次数或自动补调用来过预算测试。

## 候选最小处置与后续门禁

建议获产品修改授权后，优先为**同root、同job文件**的读取/扫描/插入/更新建立共同协调；保留内部无锁读取供已持锁的update使用，防止简单给get套现有queue导致递归死锁。先用受控读句柄与并发轮询证明资源协调有效，再核查独立RecoveryRegistry扫描及多个store实例，不扩展为无依据的全盘锁。

保持原rename次数/退避、错误可见性、取消/存储恢复、预算/Provider/Q02规则不变；本轮没有实施这一候选方案。若协调后仍捕获无本进程活动读取的拒绝，再取原生占用者/系统文件事件证据，不根据进程名单猜测。当前宿主没有可直接使用的handle/Procmon命令；读取进程列表不构成文件占用归因。

处置后才在最终逐字节副本执行默认并行完整suite（0skip）、tsc/Vite和受影响预算/恢复/取消/HTTP/React/安全回归。**本轮没有根因处置，未新跑完整验收、不签PASS。** 原验收298/300及原施工299/300均保留。
