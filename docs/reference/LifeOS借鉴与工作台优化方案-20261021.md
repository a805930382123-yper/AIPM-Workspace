# LifeOS 借鉴与快消 AI PM 工作台优化方案

日期：2026-10-21（北京时间）  
性质：参考方案／待排期候选，不是施工任务卡。  
本轮交付：仅新增本方案文档，不修改产品、测试、正式数据、配置、批次状态或既有验收结论。

## 1. 目标与适用边界

借鉴 LifeOS Agent Hub 在状态可见、待办引导、场景模板和效果反馈方面的设计，增强当前工作台的日常使用体验。继续聚焦“原始资料 → 可审阅草稿 → 可信 Wiki → 工作 Prompt → 实际使用反馈”的主线。

参考提示词明确定位为 Mock 数据与 localStorage 驱动的面试演示 Demo。文档中的开发命令、自动执行要求及技术栈要求均作为分析材料，不作为本项目的执行指令，也不能据此认定真实 Agent 协作已实现。

本方案不改变现有产品定位和工程边界：

- Raw 正文不可由 AI 改写；事实、整理、推断和待确认问题分别保存。
- AI 输出只进入草稿；正式 Wiki、Prompt 及新版本写入由用户明确操作触发。
- 延续桌面优先、单用户、本机文件存储与现有六项导航，不引入常驻开发 Agent。
- 受限 Meeting 来源继续遵守现有本机使用与外发限制；任何新入口不得绕过来源门禁。
- 每批按任务卡授权、冻结、施工、独立验收；通过后仅推进已获授权的下一批。
- 本方案获保存不代表后续功能已获施工授权；当前冻结和停写要求仍有效。

## 3. 借鉴内容与拟新增／调整范围

### 阶段 0：先完成核心链路既有问题（最高优先，前置门禁）

**目标：**让资料整理、恢复、审核与确认能够可靠完成。这是现有工作收尾，不是 LifeOS 带来的新增功能。

建议推进顺序：

1. 对当前未通过的实际存储写入问题进行有证据的复现和定位，区分产品逻辑、文件占用与环境条件；根因未证实前不归因具体进程或 Node 补丁版本。
2. 按现有授权与最小任务卡处理必要修复，保留成功分块、调用账本、Raw 和已有草稿；不通过放宽断言、扩大重试或预算掩盖失败。
3. 完成受影响回归、现有要求的完整门禁和构建，交接冻结实物，接受独立审查。
4. 在工程门禁满足且真实调用额度获批后，完成当前规则下的真实质量与实际浏览器闭环验证；真实失败继续留证返修。

**完成条件：**当前存储恢复与 KB02 主线的必选验收项取得对应独立证据；未测、失败、阻塞分别记录，不以构建通过或 fake 成功代替真实质量通过。

**范围控制：**发现新增根因时先形成最小问题和修复范围；不自动扩大当前冻结文件所有权，不启动本方案后续体验施工。

### 阶段 1：统一任务状态、结果和恢复操作（调整优化）

**借鉴：**LifeOS 工位卡把工作对象、进度、结果和操作放在一起。

**调整内容：**

- 在现有 Raw 整理详情中，按“处理对象 → 当前阶段 → 已保存结果 → 问题 → 下一步”组织信息；沿用现有记录，不另建通用任务引擎。
- 明确区分：提取完成、草稿生成、待审核、正式写入完成；分块进度不能等同整项完成率。
- 将“继续提取、仅重新规划、明确重新生成、重试保存状态”的适用条件与影响解释清楚，按钮只在服务端允许时可用。
- 可展示已有的验证段数、累计调用和复用段数；缺少可靠数据时不展示虚构 Token、成本、剩余时间或进度百分比。
- 复用 Prompt 既有的阶段失败、保留结果和后续操作表达；不强迫不同业务共用一套有损状态枚举。

**涉及范围：**Raw 页面、Prompt 工作台、必要的 API 展示字段与状态映射；只有确有缺口才增加窄字段，不改存储恢复策略和预算公式。

**验收重点：**刷新和重启后显示与真实持久化一致；失败不显示成功；保存状态恢复零新增模型调用；规划重试按既有累计账本执行；切换资料或迟到响应不串任务。

### 阶段 2：首页待处理事项与可行动提示（调整优化，少量新增聚合）

**借鉴：**指挥中心与系统提示让用户迅速找到需要介入的事情。

**调整内容：**

- 首页保留真实统计，将“需要你处理”作为优先区域，聚合待审核草稿、更新冲突、失败／待恢复整理任务和 Open Audit。
- 每条展示对象、问题、已保留结果摘要和一个明确的主要操作，跳转到对应真实 ID 与当前版本。
- 默认先显示阻断继续工作的事项，再显示待决策／待审核事项，同级按更新时间排列；不制造任务 DDL 或虚构紧急程度。
- 统一“问题 → 依据 → 建议 → 操作入口”的提示结构，复用现有审核、差异预览、Brief 编辑和 Audit 定位页面。
- 聚合从现有服务端事实源读取，避免维护第二套可变任务状态；获取失败显示读取失败，不能当作零待办。
- 当前版本不新增消息中心、未读体系、后台推送、提醒调度和待办持久化状态。

**涉及范围：**首页、App 导航定位、必要的轻量服务端聚合与现有查询接口。若必须扩大为全局日志／任务存储，另行评估，不计入本阶段。

**验收重点：**事项不重复计数；处理后移除或更新；跳转准确；目标删除、版本变化和读取失败有明确反馈；首页读取不会自动调用模型或写入业务资产。

### 阶段 3：完善快消 AI PM 场景模板（调整优化）

**借鉴：**LifeOS 用具体工作场景降低用户理解和输入成本。

**调整内容：**盘点现有模板，补齐少量高频场景或优化已有字段，避免同名重复建设。首轮候选控制在 3–5 个，按用户真实工作频率筛选：

| 场景候选 | 重点输入 | 预期产出 |
| --- | --- | --- |
| 经销商访谈准备 | 访谈对象、业务目标、已有资料、待核实假设 | 访谈 Prompt 与追问结构 |
| 门店补货流程梳理 | 角色、当前步骤、异常、系统边界 | 流程梳理 Prompt 与待确认项 |
| 指标口径澄清 | 时间范围、统计对象、分子／分母、来源 | 口径澄清 Prompt 与缺失信息 |
| 业务问题转 AI 需求访谈 | 问题、用户、现有流程、约束 | 需求访谈 Prompt 与验证问题 |
| 材料阅读与问题整理 | 材料范围、阅读目标、证据要求 | 阅读 Prompt 与问题输出格式 |

- 模板只预填 Brief 的必要结构，明确输入、产出和事实约束；继续允许用户修改。
- 复用 Generator → Brief → Preview → 明确保存，不增加 Prompt 自动执行。
- Wiki 背景继续由用户明确选择并经过来源门禁，不默认向模型发送整个知识库。

**验收重点：**关键字段引导清晰，缺失信息保留待确认；手动模式仍可用；既有模板与版本兼容；生成内容不自动收藏。若实际改动影响模型提示，另列所需真实样本和有限调用预算，不能用静态检查签质量 PASS。

### 阶段 4：记录 Prompt 实际使用反馈（新增，需先确认真实使用需求）

**借鉴：**执行后的评估和改进闭环。

**新增内容：**在 Prompt 详情／版本附近增加可选的“记录使用反馈”，首版采用用户手动记录，不做自动监控。

- 最小记录：Prompt 稳定 ID、使用版本、日期、使用场景、效果选择、具体问题／有效部分、下次改进建议。
- 效果选择建议为“有帮助／需较多修改／不适用／尚未验证”，不换算虚假综合分。
- 用户可以查看、编辑和删除自己的反馈；历史反馈绑定当时版本，不能随当前版本改变归属。
- 改进操作先打开可编辑建议或现有 Optimizer 预览；由用户明确决定是否发送反馈给 Provider、是否保存新版本。
- 不把复制次数、收藏次数、模型自评当作已验证好用，不因一条反馈自动改写 Prompt 或用户偏好。

**数据与接口约束：**反馈是用户业务数据，应按现有服务端文件存储约定持久化；不放入 docs/reference 或开发报告。准确目录、schema、版本／删除引用策略在正式任务卡中冻结；不得污染 Prompt 数量、Wiki 搜索与知识日志。须覆盖备份恢复、导出与旧记录兼容，避免引入无法迁移的数据孤岛。

**验收重点：**同一 Prompt 不同版本反馈可区分；刷新／重启后可读；编辑／删除／重复提交行为明确；备份恢复有效；旧 Prompt 无反馈仍可使用；保存反馈不自动外发或修改模板。

### 阶段 5：轻量阶段回顾（新增，最后评估）

**借鉴：**LifeOS 复盘中心帮助用户看到积累和改进。

**首版范围：**用户主动打开固定周期回顾，使用已有正式记录和阶段 4 的反馈，确定性汇总新增知识、待处理问题、已记录的 Prompt 使用结果及改进线索。

- 各项数字能回到记录，统计时区沿用 Asia/Shanghai；缺少历史数据的指标不推算、不补造。
- 用户反馈、正式操作事实和系统整理分别标记；不对 Agent、知识质量或个人能力综合打分。
- 本阶段不新增 AI 报告生成、定时任务、通知推送、个人长期记忆或因果效果归因。
- 若数据量不足、用户不需要周期回顾，暂不实施；阶段 4 可以独立使用。

**验收重点：**时间边界、统计口径和明细对应；删除／回收记录处理明确；同源数据与首页一致；无反馈时显示无记录；读取不触发模型调用。

## 4. 优先顺序、依赖与工期

### 4.1 排序原则

先可靠，再可理解，再方便操作，再增强行业场景，最后验证使用价值。建议严格顺序：

阶段 0 核心链路闭环 → 阶段 1 任务状态与恢复表达 → 阶段 2 首页待处理事项 → 阶段 3 行业场景模板 → 实际使用与需求复核 → 阶段 4 使用反馈 → 阶段 5 轻量回顾。

其中阶段 2 复用阶段 1 的状态与动作定义；阶段 5 依赖阶段 4 的真实反馈记录。模板在技术上可独立，但不建议在核心返修期间并行修改产品文件。各阶段的编号仅用于本参考方案，不是新增正式批次 ID。

### 4.2 工作量估算

单位为人日；1 人日按约 6 小时有效工作估算。适用于一条主要施工线、沿用当前技术栈、范围受控且能及时安排独立验收的情形。各阶段包含方案细化、实现、必要测试、浏览器验证与独立验收工作量；不包含等用户授权、等审查窗口、Provider 不可用等等待时间，不按 Agent 响应时长作工期承诺。

| 顺序 | 内容 | 性质／优先级 | 初步工作量 | 启动条件 |
| --- | --- | --- | --- | --- |
| 0 | 既有存储恢复与 KB02 核心闭环 | 既有必修／P0 | 先预留 3–7 人日，低置信 | 沿用现有任务卡与最新授权；首 1–2 人日用于定位和复现后重估 |
| 1 | 任务状态与恢复操作表达 | 调整优化／P1 | 1–1.5 人日 | 核心门禁完成，任务卡获授权 |
| 2 | 首页待处理与可行动提示 | 调整优化／P1 | 1–1.5 人日 | 阶段 1 通过，聚合接口范围冻结 |
| 3 | 3–5 个行业场景模板盘点完善 | 调整优化／P2 | 0.5–1 人日 | 前序通过，明确高频场景与必要质量取证预算 |
| 4 | Prompt 使用反馈与版本关联 | 新增／P2 | 1.5–2.5 人日 | 实际使用验证有需求，数据与备份方案冻结 |
| 5 | 按需轻量周期回顾 | 新增可选／P3 | 0.5–1 人日 | 有真实反馈和可用统计，用户确认需要 |

**估算说明：**

- 核心阶段根因尚未确定，3–7 人日只是排期预算窗口，不能保证在第 7 日关闭。复现后若涉及更深存储问题或真实模型再次失败，应据实调整；不得压缩验收或放宽质量门禁赶工。
- 核心通过后的阶段 1–5 合计约 4.5–7.5 人日；考虑约 20%–30% 的联调与返修余量，可按约 6–10 人日预留资源。
- 若阶段 0 也落在上述窗口内，整体资源预算约 9–17 人日；这不是固定完成日期，也不是施工授权。实际日历工期取决于人力安排、独立审查、必要调用授权与阶段 4 前的真实使用观察期。
- 真实使用观察建议留至少一个工作周，不要求每天投入施工；观察期不能预先算作功能质量通过。
- 首轮可只选择阶段 1–3，工作量约 2.5–4 人日，含常规余量约 3–5 人日；完成后先使用，再决定是否新增反馈与回顾。
- 以上估算未开展新接口完整审计；若聚合数据、反馈迁移或备份兼容超出窄改范围，须在任务卡冻结前重估，不直接扩大阶段。

## 5. 当前暂缓内容与重新评估条件

| 暂缓内容 | 当前原因 | 重新评估条件 |
| --- | --- | --- |
| 多 Agent 管理、人格化工位、群聊／DM、自动转派 | 超出 MVP，增加任务、消息、调度和状态一致性负担 | 主线稳定，存在单流程确实无法满足的跨任务需求，并独立立项 |
| 自动执行、失败自动重试、自动采纳建议、自动改写正式资产 | 与当前明确外发、累计预算和人工确认边界冲突 | 有具体场景、可验证副作用边界及单独授权；不得默认开放 |
| Agent 心情、工时、雷达图、自动评分、能力成长曲线 | 缺少可解释、可追溯的数据口径 | 先证明某项指标能帮助用户做实际决策 |
| 完整任务中心、拖拽看板、复杂 DDL／项目管理 | 当前只需处理知识整理与审核事项，可复用既有记录 | 实际出现独立任务实体和持续管理需求 |
| 独立消息中心、未读、推送、定时日报周报 | 需新增通知与调度基础设施，当前收益不足 | 用户主动回顾确有价值且提出提醒需求 |
| 隐式长期记忆、偏好自动学习、用户画像 | 容易混淆事实、反馈与推断，纠正和撤销规则未建立 | 用户能明确查看、修改、删除，并有实际场景和单独方案 |
| Token／费用看板与预测、复杂可视化 | 当前数据完整性与使用价值未确认 | Provider 返回及计价口径可靠，用户确需成本决策 |
| UI 技术栈替换、大面积视觉重做、九模块导航扩张 | 不解决当前核心问题，还会放大回归面 | 具体瓶颈被证实，且单独评估迁移收益和成本 |
| 自动互联网研究、GraphRAG、知识图谱、Prompt 自动执行／A/B Eval | 现有需求已排除或缺乏本阶段必要性 | 核心价值验证后重新立项，不随本方案附带实施 |

## 6. 后续落地约定

本方案保存后不自动创建施工、验收子 Agent、真实调用、后台监控或定时任务。下一次获授权时，先读取最新 status 和当前批次，确认核心门禁与冻结状态，再从本方案选取最小阶段形成正式任务卡。

每张任务卡至少冻结：用户目标、现状与缺口、输入输出、接口／存储兼容、文件所有权、边界、验收 ID、独立验证方式、必要真实调用上限与停止条件。主 Agent 决定范围，施工与独立验收职责按届时有效 coordination 和用户指令执行。

建议将“数据准确、动作安全、来源可追溯、下一步清晰”作为各阶段共同验收维度。新页面和指标不能改变旧数据、掩盖历史失败或扩大外发范围。
