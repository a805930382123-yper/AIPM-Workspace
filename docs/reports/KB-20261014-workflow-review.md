# 知识库AI主流程调整审查（2026-10-14）

状态：方案审查完成，未施工、未调用Provider、未处理用户Raw。用户本轮提出知识库生成/维护角色与手动新建体验不符，要求核对调整方向。本文件形成具体界面与流程方案，不把旧FULL3 FAIL改为PASS。

## 原始目标与现状

需求§4/8–10明确LLM负责文档理解、拆解、分类、关联及更新建议；用户负责导入、预览、确认。正确主线为 Raw → LLM结构化知识建议 → 用户审核 → 正式Wiki。§22–24规定去重、更新建议、冲突保留，确认前不能覆盖正式知识。

实际产品已有提取/草稿/提交（B04）及去重/更新/综合（B05），但入口层没有完整呈现该主线：

|---|---|---|
| app/pages/WikiPage.tsx:121/125/183 | 新建Wiki打开空白模板/手动表单 | 用户从知识库开始创建时会以为需要自己写全部内容 |
| app/pages/HomePage.tsx:21 | 流程仍写“手动整理为Wiki” | 首页表达与原始AI知识加工定位不一致 |

真实Provider方面，FULL3短文提取60秒超时、综合90秒超时；没有真实提取入库/更新成功证明。入口调整与实际AI可用性都需要验收，按钮更名不能消除超时。

## 建议用户流程

导入/选择普通Raw → 生成Wiki草稿 → 展示建议新增/建议补充/可能冲突 → 用户勾选、必要编辑 → 确认写入 → 阅读正式Wiki及来源/日志。

一条Raw可生成多页，按明确知识主题拆成Source/Concept/Entity/Business Process/Metric等。多来源Synthesis保持独立显式选择来源。用户主要审核结果，标题、类型、分类、正文、来源链接由已校验AI建议预填。

### 1. 知识库与首页

- 知识库主按钮改为“从Raw生成Wiki”：选择已保存且可AI处理的Raw，复用真实提取任务；没有Raw时进入导入。
- 手动表单保留为次级“手动创建”，包括空库提示、首页快捷入口及编辑器标题，避免与AI生成入口同名。
- 首页流程改为“导入Raw → AI生成/更新知识草稿 → 审核确认入库”；待审核计数可点击打开草稿列表。
- 知识库展示待处理Raw/处理中任务/待审核草稿的入口，正文列表依然只含正式Wiki。

### 2. 导入后的衔接

- 建议提供主操作“保存并生成Wiki草稿”与次操作“仅保存Raw”；前者为明确生成动作，普通保存、浏览或页面加载不隐式发送已有资料。
- 文件/粘贴导入成功后直接使用服务端已返回的Raw ID启动同一提取流程，不要求再上传或手工填写Wiki。
- 提取失败时明确“Raw已保存，Wiki草稿未生成”，可重试同一Raw；不要让重试重复导入。部分文件提交/待恢复仍按现有真实状态处理，尚未完整成功时不直接启动AI。
- 处理中显示步骤/取消，完成提供“审核Wiki草稿”；跨导航/刷新/重启能从待审核入口继续。

### 3. AI维护已有Wiki

- 生成草稿后自动运行现有去重候选查询，明确呈现“建议新增”“可能补充已有页”“存在冲突/待确认”，代替用户逐页主动找检查入口。
- 对候选匹配给出原因与来源，允许用户选择目标或明确新建/暂不处理；模型或匹配算法不能未经确认决定覆盖。
- 选择目标后复用已有wikiUpdate能力，将目标Wiki、新Raw及证据输入LLM，生成旧文/新增/冲突并列预览。若需要AI提前推荐新增或补充，须新增受来源策略约束的候选Wiki摘要上下文；只取相关页、有长度上限，避免发送全库。
- 确认更新保留旧来源、人工备注和相反口径，检查目标revision；过期预览需重新审核。跨页组合确认如果新增与更新共存，必须明确逐项提交状态，不能声称现有两种提交接口已经是同一事务。

## 实施范围与顺序建议

1. KB-UX：首页/知识库主入口、手动入口命名、导入衔接与待审核导航。复用现有startExtract/任务/草稿，改App、HomePage、WikiPage、RawPage及对应交互。验收实际按钮路由/Raw ID/取消/重复点击/切页与迟到响应。
2. KB-MAINT：自动候选发现与新增/更新/冲突预览；按需要补候选摘要给LLM。冻结来源策略、上下文预算、revision及逐项提交接口后再施工，不把界面列表等同已实现自动维护。
3. REAL-KB：处理FULL3真实提取延迟阻断，实测短文与长文策略、正式入库、重复来源补充、冲突保留与重启审核。与入口施工分别报告，真实未成功则继续BLOCKED。

本次没有授权自动覆盖正式Wiki；继续遵守用户明确确认写入、Raw不可改写、事实/整理/推断/待确认分开。新Meeting来源仍local_only，选择器排除并说明不可AI处理，前后端都执行门禁。普通Raw生成操作应说明所选资料会发给配置Provider。

## 验收样例

- 从知识库“从Raw生成Wiki”选择已导入普通Raw，实际LLM得到预填知识草稿，确认前无正式写入；用户确认后Wiki/Source/Index/Log一致且Raw原文未变。
- 从导入主操作直接走同一链，仅保存Raw不触发Provider；生成超时不丢Raw，重试不重复导入、双击不重复任务/正式页。
- 新Raw补充已有主题，自动呈现候选，用户确认目标后真实更新预览保留人工备注/来源；同指标两种口径显示冲突而非静默选一个。
- 待审核计数与列表可进入提取/更新/综合草稿，刷新/重启后恢复；选择切换或迟到任务不强行跳转用户正在看的资料。
- 手动创建仍可用，会议来源仍不能外发或成为Wiki背景。实际Provider质量与离线交互测试分别验收，不能用fake签真实AI成功。
