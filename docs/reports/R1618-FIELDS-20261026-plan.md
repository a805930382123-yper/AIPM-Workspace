## 结论与现有责任

下一最小能力应是：用户在 Concept / Business Process 的指定字段中选择本页已有证据摘录，并能另写明确标记的人工说明；AI 机会的自由文字固定标记为“分析建议”。来源选择与人工说明独立保存。无需改 LLM 输出协议，不自动依据关键词归位，也不将可编辑文字因附有证据就认定为来源事实。

PRD §13 / §15 的字段清单及上一轮 `render.ts` 结构修复继续使用。Concept 一句话解释、定义等 8 个普通字段支持本方案；待确认问题继续使用现有 R12 标记和原问题栏，来源继续使用系统 Source / Raw 关联。Process 14 个字段均支持，包含 AI 机会；来源由既有关联派生。标题继续由页面标题编辑器承载。

## 确定存储与渲染设计

仅新增可选 `DraftPage.templateFields`，普通页面 patch 可编辑。同一结构也加入客户端 DraftPage 类型。

```ts
type TemplateFieldContent = {
  evidenceIds: string[];
  humanText?: string;
};
// key 仅允许当前类型在 rules/page-templates.yaml 中既有的字段 key。
// Concept 排除 open_questions；Source 不是人工可写字段。
templateFields?: Partial<Record<TemplateFieldKey, TemplateFieldContent>>;
```

Concept key：`one_line_explanation / definition / why_important / business_context / characteristics / common_categories / relationships / scenarios`。Process key：`business_goal / roles / trigger / inputs / steps / outputs / systems / rules / human_judgement / exceptions / pain_points / ai_opportunities / metrics / related_knowledge`。采用现有规则中的拼写，不新增术语。小型 `services/wiki/template-fields.ts` 只共享这两类固定键及类型，替代当前 renderer 内分型常量；它不是可扩展字段引擎，不添加注册、迁移或通用校验框架。UI 字段标题与顺序继续取已有 Wiki schema。

`evidenceIds` 是本页现存 source_evidence 的引用，不复制事实、引文或位置，也不新造 fact ID。选择列表直接展示 ID 与完整原摘录；字段正文逐字输出选中 evidence.quote 与证据 ID，明确标“来源摘录（用户归位）”。保留其中否定、未知、未来条件和完整边界，不截去限定词，不从摘录自动改写成定义、角色或步骤。公共来源事实、完整证据目录及 Source / Raw 链接继续保留，以便核对。

同一证据可以由用户明确选择到多个字段；只限制单个字段内相同 ID 不重复。拒绝不存在、其它页面或其它 Raw 的证据 ID。成员关系和 Raw/区间校验复用现有证据结构与 assertEvidenceStillValid，不另建来源目录。引用合法只能证明摘录出处，不能机械证明字段语义正确；归位语义由用户在原逐页显审中确认。

`humanText` 是用户可自由编辑的说明，不回写 source_facts 或证据，不改 open_questions / humanReview 原目录。普通字段正文标“人工说明（待核对）”；AI 机会字段标题及文字固定标“分析建议”，不声称来自模型或已经实施。AI 机会如另选原摘录，同样只标“来源摘录（用户归位）”，不预判摘录与 AI 的语义关系；不把“尚未上线/未来建议”转成现行业务事实。空引用且无人工文字的字段仍显示待确认，不要求全字段必填。

一句话解释不再把规划标题自动视为已归位内容：Concept 任一新字段有值即启用新模板，正式“一句话解释”只使用其自身所选来源摘录及独立人工说明；该字段未填写时显示待确认，不以旧 one_line_definition 补成已归位解释。原 one_line_definition 继续保留在草稿记录及独立“原草稿一句话说明（未归位）”显示。清空全部新字段并归一为缺省后，回到旧页面表现；这种回退不代表新解释完成或质量通过。无 templateFields 的旧页面继续原表现，不自动补空map、不写盘、不使审批失效。Process 现有通用一句话栏保留，用户可继续用原编辑器修改。

## 最小 UI 与现有操作的关系

在 DraftReviewPage 两类页面卡增加按模板顺序展示的“字段归位”区：每字段提供本页证据多选和人工说明文本框。保留原事实及证据只读；新文字框始终有明确来源标签。保存使用原“保存编辑”；保存成功后从服务端新 view 显示字段内容。可在现有卡内提供一处服务端正文预览，内容取 renderedBody，避免用户只看输入框而不知道正式标签。编辑未保存时沿用 dirty 提示，不显示成当前已保存预览。

不新增“批量已审”按钮。用户先保存编辑，再用原逐页显审，勾选并确认新建正式页面；刷新后读取真实正式文件。本轮仅覆盖人工字段编辑到新建正式页，不覆盖更新已有 Wiki。对于含非空 templateFields 的候选，现有“生成旧 Wiki 更新预览”动作必须明确阻断并保留原草稿，服务入口也应拒绝该输入，不能仅隐藏按钮后仍允许直接请求静默丢字段。无字段候选的既有更新路径保持原样，不扩 LLM 协议或重做更新链。

为避免既有来源移动/合并操作产生悬空，采用明确、可撤销的最小限制，不写自动语义迁移：

- **完整 unit 移归**：已有字段引用保持只读引用。对拟移归后的页面来源目录做现有引用有效性检查；若引用 ID 消失或同 ID 对应的 Raw/quote/start/end 改变，则原子拒绝这次移归，提示先撤销对应字段引用再移动。未引用的 unit 仍可正常移动。不清掉人工文字或静默改绑到外页证据；对照移归前的内存记录即可，不持久化新身份或哈希。
- **合并**：本轮不支持带非空 templateFields 的合并。若任一目标有非空字段，动作在写盘前原子拒绝并完整保留原字段；用户可取消操作并继续编辑原页。UI 直接说明该限制，无字段的原合并路径继续可用。不提供自动字段合并或无损迁移，也不把保存后清空当作常规兼容流程。
- **类型切换**：本轮不支持带非空字段的类型切换，动作原子拒绝，原内容完整保留；无字段的原切型继续可用。“清空字段归位”仅作为显式删除当前归位内容的编辑动作：未保存可刷新撤回，清空并保存后本方案不提供恢复能力；草稿保存不是历史备份。不得将清空描述为可恢复或无损迁移，不自动改义旧字段。
- **删页**：保留原行为；页面字段随该页删除，原来源 unit 进入原未解决池，必须重新解决/显审才能正式提交，不向其它页自动分配字段。

上述引用检查须在 deriveReviewPages 之后再确认一次；现有 patch 先 validatePage 再 derive 的顺序不能单独保障新增引用。直接修改 JSON 的无效字段也应在正式确认前的既有 assertEvidenceStillValid 路径拒绝；这是新增字段自身的必要完整性检查，不新增验收体系。

## 审批失效与兼容

新增字段的选择、自由文字、清空、类型变动均参与原 candidateContent；实际改变后复用统一 approvals=[] 与 revision 增加。无操作保存不应失效，UI 不应给旧草稿自动补空 map 导致假变更。新类型中的 templateFields 没有值时不持久化属性；`undefined / 空map / 空项` 在服务写入时归一为缺省，读取不写盘。

旧草稿没有属性即按当前占位/原一句话表现读取，不触发模型、后台迁移或隐式 GET 写盘；只有用户明确保存新编辑时写入。已 confirmed / committing 的旧草稿继续按原生命周期限制，历史冻结 manifest 按原 snapshot 恢复，不用新 renderer 重新生成旧正文。新增属性存在但结构/键/引用非法时明确报错，不能忽略成空字段后继续正式保存。
