# Meeting Hub｜会议档案中心开发提示词（MVP）

## 一、任务目标

请在现有「快消 AI 产品经理工作台」中新增一个可以真实操作的 **Meeting Hub（会议档案中心）**。

这是现有项目的增量开发，不是创建一个新项目。

**开发前必须先阅读现有代码和架构，识别已有的数据库、文件存储、Raw知识库、路由、UI组件和服务层，并尽量复用。**

不要因为增加 Meeting Hub 而重新搭建一套独立系统，也不要重构原有的 LLM + Wiki 和 Prompt 模块。

本模块主要面向快消行业 AI 产品经理、AI 解决方案人员及相关业务岗位，用于管理：

- 客户需求对接会议；
- 项目进展汇报；
- 客户拜访；
- 方案评审；
- 内部工作会议；
- 行业学习及培训会议。

首版核心目标：

**统一管理会议资料、明确资料保密与处理权限、支持会议分类检索，并与现有知识库建立安全且可追溯的关联。**

必须实现可运行的功能，不要只制作静态界面。

---

## 二、与飞书的协作方式

本模块采用：

**飞书云端处理 + 工作台本地归档**

业务流程：

1. 使用飞书妙记进行会议录音、转写；
2. 使用飞书智能伙伴生成会议纪要；
3. 录音及云文档保留在飞书云端；
4. 用户在工作台新建会议档案；
5. 保存飞书妙记录音链接、飞书纪要文档链接；
6. 如资料允许本地保存，用户可导出 Markdown 纪要并导入工作台；
7. 工作台负责会议分类、归档、检索、阅读及管理；
8. 获得适当授权的纪要，可通过现有 Raw → Wiki 流程进行知识沉淀。

首版不接入飞书 API。

不要开发：

- 飞书 OAuth；
- 飞书账号绑定；
- 自动获取云端会议；
- 自动同步飞书文档；
- 自动下载录音；
- 云端录音播放器；
- 录音语音识别；
- AI自动生成会议纪要。

飞书录音在工作台中只作为**云端来源链接**保存。

链接打开时跳转飞书，由飞书原有登录和访问权限控制。

工作台不声称拥有飞书录音的访问或管理权限。

## 三、产品整体结构

左侧导航增加：

**会议档案**

点击后进入 Meeting Hub。

首版仅实现：

1. 会议列表；
2. 新建及编辑会议；
3. 会议详情；
4. 分类、标签、搜索与筛选；
5. 飞书云端来源管理；
6. 获授权会议纪要的本地导入与编辑；
7. 资料保密分级与处理限制；
8. 与现有 Raw 知识库的安全关联。

不要增加复杂的会议数据看板、任务管理或客户 CRM。

## 四、会议数据结构

以“一场会议 = 一份会议档案”为核心。

每份会议档案至少记录：

### 基本信息

- meeting_id：唯一稳定ID；
- title：会议名称；
- meeting_date：会议日期，可附时间；
- meeting_type：主要会议类型；
- tags：业务标签，可多选；
- customer：关联客户名称，可为空；
- project：关联项目名称，可为空；
- description：补充备注，可为空；
- created_at；
- updated_at。

客户、项目首版只作为轻量关联字段，不创建独立 CRM 或项目管理系统。

### 飞书来源

- recording_url：飞书妙记链接，可为空；
- minutes_url：飞书云文档链接，可为空。

只接受合法 HTTPS 链接，避免保存脚本协议或危险链接。

### 本地资料

- imported_minutes：导入的原始会议纪要；
- editable_minutes：可编辑纪要副本；
- original_filename；
- imported_at；
- raw_source_id：对应现有 Raw 的 ID，可为空。

### 安全信息

- confidentiality：资料保密等级；
- storage_mode：存储方式；
- local_storage_authorized：是否确认获准本地保存；
- external_ai_authorized：是否确认获准使用当前外部AI服务处理；
- raw_transfer_authorized：是否确认获准进入知识库；
- policy_updated_at。

所有新增字段必须设置安全、兼容的默认值。

不要因为会议档案没有附件或飞书链接，就导致创建失败。

## 五、会议分类

首版采用：

**一个主会议类型 + 多个业务标签 + 可选关联客户/项目。**

### 主会议类型

默认提供：

1. 需求对接；
2. 项目进展；
3. 客户拜访；
4. 方案评审；
5. 内部例会；
6. 培训学习；
7. 业务复盘；
8. 其他。

允许用户管理和扩展会议类型。

每场会议只选择一个主类型。

### 业务标签

允许多选，例如：

- AI Agent；
- 产品需求；
- 渠道；
- 门店；
- 动销；
- 市场竞争；
- 产品优化；
- 数据指标；
- 客户沟通。

业务标签由用户自行添加和维护。

不要把标签写死在代码中。

### 关联对象

允许填写：

- 客户；
- 项目。

同一客户、项目下的会议可以筛选查看。

首版不实现客户档案自动关联或项目进度管理。

## 六、资料保密等级

这是首版必须落实的核心设计。

资料分为四级：

| 等级 | 含义 | 默认处理方式 |
|---|---|---|
| Public | 公开资料 | 允许正常本地归档 |
| Internal | 一般内部资料 | 需确认授权后才能本地保存 |
| Sensitive | 敏感客户或业务资料 | 默认仅建立云端索引，不保存正文 |
| Restricted | 严格保密资料 | 原则上只保留最少且获准登记的元数据 |

对于没有明确分类的会议：

**默认按照 Sensitive 处理。**

不得默认认为所有会议资料都可以上传第三方大模型。

保密等级是工作台的数据处理规则，不等于真实的企业访问授权。

如果当前产品是单用户本地系统，不需要为此开发复杂的账号、角色和 RBAC 系统。

---

## 七、存储方式

首版提供两种方式。

### 模式A：云端索引

保存：

- 会议名称；
- 日期；
- 类型；
- 标签；
- 获准登记的客户/项目标识；
- 飞书录音链接；
- 飞书纪要链接。

不保存：

- 本地录音；
- 会议逐字稿正文；
- 会议纪要正文。

适合敏感会议。

注意：会议名称、客户名称、链接本身也可能涉及敏感信息，Restricted 资料必须尽量减少这些字段，不应强制填写或保存敏感链接。

### 模式B：本地归档

在云端索引基础上，允许导入：

- Markdown会议纪要；
- 直接粘贴的会议纪要文本。

保留：

- 原始导入版本；
- 可编辑工作版本。

此模式仅在相关资料允许本地保存时使用。

对于 Internal 和 Sensitive 资料，切换至本地归档前必须明确提示并要求用户确认已获得适当授权。

Sensitive 资料即使允许本地保存，也不代表可以发送外部 LLM。

Restricted 资料在 MVP 中禁止导入本地正文、转入 Raw 或发送 AI；如确有业务需要，应通过未来独立的企业授权流程处理，不在首版绕过。

---

## 八、AI处理权限

**资料保密等级、本地保存权限、外部AI处理权限、知识库入库权限必须分别管理。**

默认：

- 不自动调用 LLM；
- 不自动上传会议纪要到外部AI；
- 不自动提取知识；
- 不自动写入 Wiki；
- 不自动发送会议正文到 Prompt Generator。

本模块首版本身不需要调用 LLM。

如果将来允许使用现有 LLM + Wiki：

必须先检查：

1. 资料是否允许进入本地知识库；
2. 是否允许由当前配置的 AI 服务处理；
3. 资料是否被标记为 Restricted；
4. 用户是否主动发起操作。

只有满足条件才能继续。

**用户勾选“已获授权”只是确认记录，不能替代真实的公司授权。**

敏感或严格保密材料不得因用户在普通界面修改一个布尔字段而自动解除系统限制。

权限检查必须放在服务层执行，不能只靠隐藏前端按钮。

如果现有 Raw / LLM Service 无法识别资料的处理限制：

**不要将敏感资料接入自动 AI 入库链路。**

必须明确提示当前不支持安全处理，而不是绕过限制。

## 九、会议列表

Meeting Hub 首页采用简洁列表式管理。

每条会议显示：

- 会议标题；
- 日期；
- 主会议类型；
- 业务标签；
- 客户/项目；
- 保密等级；
- 归档状态。

归档状态至少包括：

- 仅云端索引；
- 已导入纪要；
- 纪要导入失败。

提供：

- 新建会议；
- 搜索；
- 按会议类型筛选；
- 按标签筛选；
- 按客户/项目筛选；
- 按保密等级筛选；
- 按日期排序。

搜索应优先针对已保存的标题、标签、客户和项目进行，不需要首版实现会议语义搜索。

对于 Restricted 资料，不要在列表中展示未经授权的敏感摘要。

## 十、新建会议

新建会议时展示简洁表单。

基础必填：

- 会议名称（严格保密会议可填写不含敏感信息的代称）；
- 会议日期；
- 会议类型。

可选：

- 业务标签；
- 客户；
- 项目；
- 备注；
- 飞书录音链接；
- 飞书云文档链接。

同时设置：

- 保密等级；
- 存储方式。

不要强制用户上传会议纪要。

允许先建立一份只有会议基本信息和飞书链接的档案，后续再补充纪要。

## 十一、会议详情页

一场会议对应一个统一详情页。

页面依次展示：

### 1. 基本信息

会议标题、日期、类型、标签、客户/项目、备注。

### 2. 飞书来源

展示：

- 打开飞书妙记；
- 打开飞书会议纪要。

没有链接时显示“未添加”。

不要做无法真实使用的录音播放器。

### 3. 本地会议纪要

如果已授权导入：

- 展示 Markdown 正文；
- 支持阅读；
- 支持编辑；
- 支持保存；
- 支持取消编辑；
- 支持重新导入。

如果只保存云端索引：

显示：

“会议纪要保存在飞书云端，当前未在工作台保存本地副本。”

不要显示虚假的会议正文。

### 4. 资料安全信息

明确显示：

- 保密等级；
- 存储方式；
- 外部AI处理是否获准；
- 知识库入库是否获准。

### 5. 相关知识

仅在满足权限要求并已建立关联时显示：

- 对应 Raw；
- 已有 Wiki 来源关联。

没有关联时，不要伪造知识条目。

## 十二、会议纪要导入

首版优先支持：

1. Markdown `.md`；
2. 直接粘贴文本。

如现有工作台已经具备稳定的 DOCX/PDF 解析组件，可以复用，但不要为会议模块重新开发复杂解析系统。

如果当前没有成熟的 Word/PDF 解析能力，首版不强制支持。

用户可以直接从飞书云文档导出 Markdown 后上传。

导入流程：

1. 检查会议存储权限；
2. 校验文件类型和大小；
3. 保存原始导入内容；
4. 创建可编辑副本；
5. 更新会议归档状态；
6. 记录导入时间。

原始导入版本不得被编辑操作覆盖。

再次导入纪要时，应保留可追溯的版本信息或明确提示替换影响，并保证用户有机会取消。

Markdown渲染必须防止恶意脚本和不安全 HTML 执行。

---

## 十三、与现有 Raw / Wiki 的关联

**这是模块集成的重要部分，但不要重建知识库。**

会议纪要和 Wiki 的关系：

- Meeting：会议档案；
- Raw：获得授权后登记的会议原始资料；
- Wiki：通过现有 AI 整理与人工审核流程形成的知识。

用户在会议详情中可以看到：

**关联知识库**

如果权限允许，可选择：

“将会议纪要登记到 Raw”。

必须遵守：

1. 不自动导入；
2. 不自动生成 Wiki；
3. 不自动调用 LLM；
4. 不自动复制两份互不关联的正文；
5. Raw 与会议档案之间通过稳定 ID 关联；
6. Raw 必须保留会议来源和保密信息；
7. 后续 Wiki 不得自动降低来源的保密限制。

优先复用现有 Raw 文件和来源管理机制。

如果现有 Raw 系统无法安全继承权限：

先实现 Meeting 与 Raw 的只读关联或暂时禁用敏感纪要入库，不得直接绕过权限检查。

---

## 十四、数据保存和安全

必须复用当前工作台已有的持久化方式。

不要仅使用浏览器临时状态存储关键会议数据。

原则：

- 数据刷新后仍然存在；
- 本地文档保存到现有受控数据目录；
- 不存入前端公开静态资源目录；
- 不写入公开 Git 仓库；
- 不默认上传个人云盘；
- 不把纪要正文或敏感链接写入普通应用日志；
- 文件路径必须防止越权读取和路径穿越；
- 不支持的文件应拒绝导入；
- 文件错误要有明确提示；
- 数据删除前需要二次确认。

如果现有部署环境无法提供足够的本地文件保护，应明确说明限制，不能宣称“已实现企业级数据安全”。

本模块不需要建设新的企业级权限系统、云存储服务、文件加密系统或备份平台。

---

## 十五、会议删除

删除会议时必须二次确认。

需要区分：

- 删除会议档案；
- 删除工作台保存的本地会议纪要副本；
- 删除与 Raw 的关联。

不能因为删除工作台会议，就声称删除了飞书云端资料。

如果 Raw 或 Wiki 已引用相关资料，应提示存在关联。

默认不得静默级联删除已有 Wiki 知识。

## 十六、视觉风格

延续现有工作台风格。

要求：

- 复用已有导航、按钮、表单、列表及详情组件；
- 不创建另一套设计系统；
- 保持专业、简洁；

- 复杂图谱；

- 无意义动效；

## 十九、MVP验收标准

完成后必须实际验证：

### 会议档案

1. 可以新建会议；

# 最终开发原则

**Meeting Hub 第一版不是一个AI会议助手，而是一个可靠、清晰、安全的会议资料管理模块。**

核心主线：

飞书录音及纪要
→ 创建会议档案
→ 分类与保密分级
→ 保存飞书链接
→ 获授权后本地归档纪要
→ 阅读、编辑和检索
→ 经权限检查后关联现有 Raw 知识库。

优先复用现有代码。

不要过度设计。

不要为了未来可能有用的能力增加复杂架构。

**所有功能必须真实可用，所有权限必须明确，所有敏感资料默认采用保守处理策略。**
