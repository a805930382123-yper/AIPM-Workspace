## 默认分析框架

| 对象 | 字段要点 |
|---|---|
| 角色卡 | 名称；内部或外部；与产品的关系，可多选决策者、使用者、受影响者、付费方；画像；使用频率；可选关联 Wiki 页。预设角色只是可修改的建议：内部有业务员、区域经理、渠道/KA 运营、市场部、财务、IT；外部有经销商老板、经销商业务员、门店店主/店员、导购/促销员、KA 采购、消费者 |
| 使用场景与任务 | “当〔情境〕时，〔角色〕想要〔任务〕，以便〔结果〕”三段式 |
| 痛点 | 所属角色，可选关联场景；严重程度；类型分事实、推断、待验证。事实必须引用已关联 Raw 的逐字原文 |
| 现有替代方案 | 所属角色；目前怎么做；代价 |
| 价值主张 | 对谁 × 解决哪些痛点 × 比现有替代方案好在哪里；置信度分已验证和假设，假设需填写验证方式 |
| 功能 | 来源价值（除“不做”外至少 1 条）；优先级分必须、应该、可以、不做；阶段分 MVP、V1、后续；选“不做”时必须填写理由 |
| 整体构想 | 北极星、目标用户范围、不做范围、成功指标（名称、口径、目标）、风险 |
| 里程碑 | 目标周（`YYYY-Www`，与 REVIEW01 一致）、包含的功能、交付物 |

内部和外部角色并存时，买单的人和使用的人常常不是同一个。因此价值主张要按角色分别写，追溯检查也会分别看决策者和使用者是否都有价值覆盖。

## 关键产品决定

1. **从人出发**：功能必须追溯到价值，价值必须落到具体角色的痛点。追溯检查只提示、不阻止保存，由用户决定是否处理。
2. **事实、推断、待验证分开**：只有附带逐字 Raw 引文的痛点才能标为事实。Raw 被删除、受限或引文已不在当前正文时，标为依据失效，并且不自动降级或改写。
3. **构想不是正式知识**：产品构想不写 Wiki、Prompt，也不改 Raw；导出只生成下载内容。
4. **周计划只服务个人**：不做人员、甘特图、工时和自动挪动任务。顺延、放弃、拆分都由用户明确操作并保留记录。
5. **AI 只写草稿**（PB04）：输出必须引用本次输入中的对象 ID 或 Raw 原文；采纳后标记来源轮次，校验失败的结果不可采纳。
