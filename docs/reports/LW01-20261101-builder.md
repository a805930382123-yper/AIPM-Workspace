## 实现接口

Draft 增加可选 `maintenance:{version:1,context,changes}`，旧无字段草稿保留旧路径。每项包含 `changeId/pageIndex/action/targetWikiId/baseRevision/candidate/reason/summary/questions/dependsOn/decision/approval/committedOperationId`。`candidate` 是完整 Wiki 正文和可写元数据、Raw 来源集合。`action` 为 create/update/link/noop，`decision` 为 accept/defer，`approval` 绑定服务端内容摘要。

标准和深度共用提取后、规划前检索：标题/别名、关键词/标签/正文命中及少量链接扩展，最多 8 页、48,000 个 JSON 字符，确定性排序。分类相同本身不入选。仅选中正文、真实 ID/revision/sources/相关链接进入规划和后续维护调用。首次读取过滤限制来源；恢复外发前重新检查来源。维护生成使用现 Provider、结构化 schema、累计 attempts、取消及 checkpoint，没有平行模型引擎。深度原句去重不调用 Provider。

人工入口是现 DraftReviewPage 的维护分支：先列动作/主题/待核/处理清单，可定位详细项，展示确定性逐行增删、旧正文、完整候选和来源。逐项接受、编辑、暂缓、确认；编辑撤销该项批准，归属/来源目录变化撤销逐项批准。摘要包含原来源目录、完整归属、深度笔记/覆盖元数据及质量报告。未归属事实/问题阻断提交。深度复用既有 StructuredNoteEditor 的实际 noteCoverage、质量报告、确定性警告、双告知和 noteApproval，覆盖未完无法确认；noteApproval 自身不参与被确认内容，避免循环。

`POST /api/knowledge/drafts/:draftId/changes/review` 请求 `{baseRevision,changeId,decision?,title?,body?,confirmed?,digest?}`；GET 草稿返回 `changeDigests`。归属继续用原 `/api/drafts/:id/review/move`，深度审核继续用原 `/review/structured-note`。正式提交继续用 `/api/drafts/:id/confirm`，selectedPageIds 对应接受且尚未提交项的 pageIndex。原 API 返回真实 resultWikiIds，包括无正文写入项。

现 manifest 扩展 maintenance：冻结所有旧目标 `targets`（含 noop/不落盘 link）、更新前 `before`、动作、选集、实际结果 ID 及审批摘要。update 保留 ID 并增 revision，link 只改实际需要的来源关系，noop 不空增版本。标题/别名冲突门禁排除 update 自身后仍执行。确认及恢复重查版本字节、来源和完整审批/深度覆盖。前快照与变化记录在 manifest/log 中，不追加“本次更新审核”正文。

相同 Raw 自动验证并复用真实 Source。部分接受后其余项留在同草稿，后续可用新键继续；Source 保留人工正文并累计实际接受主题链接。未接受新页链接转为纯文本，索引/反链按实际写入重建。幂等先独立按 draft+key 查询，已完成同 key 同 payload 复用，不同 payload 409，不受当前选择过滤影响。

Raw 按钮改为“整理并融入知识库”，沿原阶段进度。按真实 rawId/draftId/state 读取草稿拟影响主题和实际 generatedWikiIds 的正式标题，取消迟到响应；失败明确显示“受影响主题读取失败”，不冒充没有影响。

深度待核原句以可信 fact/atom/evidence 位置或经核对的 `sourceBoundary:{rawId,start,end,category}` 为身份；reason 变化不产生新原句，独立原因合并保留。不同 Raw/位置/类别和不可靠定位不删。段落、列表、表格、路径图均处理；图表结构关系保留，重复原句处指向合并项。连续组装幂等，组装与 checkDeepNote 共用口径。完成旧草稿可读；已存笔记确与新归并规则不兼容时明确拒绝恢复并保留，不自动外发。
