## 裁决

**核心设计可采用，但下一任务卡须修正下列明确边界后再施工。** 来源摘录引用与人工文字分开、复用既有保存/显审/正式提交，是满足人工字段归位的直接方案。不要求新增模型契约、通用字段引擎、迁移框架或新摘要体系。此结论是方案审查，不是功能PASS。

1. **去除“保存后清空即可合并”的无损暗示。** 当前草稿保存不是历史备份，清空并保存会丢失这部分人工归位和说明。最小本轮可以明确不支持带非空字段的合并及切型：动作原子拒绝，原字段完整保留；用户仍可取消操作并继续编辑原页。UI直接说明此限制，不把清空作为常规无损路径。“清空字段归位”是显式删除当前归位内容，未保存可刷新撤回，保存后无本方案提供的恢复能力。无字段的原合并/切型继续可用。本轮无需为了消除限制而扩大到自动字段合并、别名迁移。若主Agent要求带字段合并也必须保留原正常能力，则应另定具体合并语义，不能同时承诺最小拒绝方案和无损合并能力。
2. **来源标签保持中性。** AI机会字段内用户选择的任意证据只能标“来源摘录（用户归位）”，不能一概叫“来源中的AI相关表述”。引用合法证明出处，不证明语义相关。人工自由文字独立标记“分析建议”；普通字段标“人工说明（待核对）”。全文摘录不删否定、未知、未来条件。
3. **把Concept一句话的回退写清楚。** 任一新字段有值便启用新模板时，未填写的一句话解释显示待确认，旧 one_line_definition 只能在“原草稿一句话说明（未归位）”独立展示。清空全部新字段并归一为缺省后回到旧页面表现；不得将这种回退宣称为新解释完成。无属性旧草稿不自动补空map、不写盘、不使审批失效。
4. **验收范围写为人工字段编辑→新建正式页。** 当前页面还存在“生成旧Wiki更新预览”入口，方案并未覆盖它消费新字段的语义。不能用本轮结果宣称更新已有Wiki也保留人工字段；施工若发现该入口会静默丢新字段，应明确阻止该有字段输入并保留原草稿，而不是新增模型输入协议。此为现有入口范围边界，不要求重做更新链或真实调用。

## 关键代码核对与操作限制

独立读取 `DraftStore.deriveReviewPages`：来源目录会依据unit归属重新派生，同ID异内容会重命名。因此只在普通patch前校验引用不足。方案提出派生后再核对引用、对照移归前实际 Raw/quote/start/end、写盘前拒绝悬空或改绑，具有具体代码依据。拒绝只影响引用确实被破坏的操作；未引用unit移动继续可用，不能笼统禁用来源整理。

独立读取 `applyMerge`：当前复制第一页并重组来源目录，未定义新增字段如何合并；仅将属性追加到DraftPage不会保全其它页字段。上述明确拒绝是有限且可验证的本轮取舍，但确实限制新填写页的后续合并，不应宣传为全部旧操作无条件兼容。

独立读取 `candidateContent` 与 `payloadDigest`：前者默认包含可写候选内容，后者手列正文相关投影。因此复用原审批失效机制并补提交投影合理，无需改human-review摘要协议。snapshot显式枚举需补新字段。字段实际修改/清空后旧审批失效；规范化后的无变化保存保留审批。校验必须同时覆盖普通patch、review移归后和正式提交前，不能只覆盖UI。
