## 1. 问题诊断

当前“AI 整理”链路已经能完成分块事实提取、证据定位、主题规划和草稿组装，但它不是完整的知识写作流程。主要差距如下：

1. **缺少整篇理解与组织。** 分块提取先得到较零散的事实，再由规划器分配到页面。原始材料中的段落关系、表格结构、概念对比和阅读主线没有被保留成一个整体。
2. **缺少知识写作阶段。** 当前组装代码将 `one_line_definition` 直接设为标题，并将 `ai_organized`、`ai_inferences`、`related_pages` 置空。输出更像“事实清单”，不是容易阅读和学习的知识笔记。
3. **正文结构表达不足。** 现有渲染主要以字符串数组生成项目符号列表，难以自然表达多级章节、表格、路径图、术语对照和边界提醒。
4. **质量检查偏结构，不偏阅读效果。** 当前门禁能检查 schema、证据和覆盖，但没有系统评估“是否讲清概念关系”“是否比 Raw 更易理解”“是否遗漏关键信息”。
5. **补充知识与原文知识容易混淆。** 参考笔记中包含 SKU 层级、Sell-in/Sell-out 等原文没有的补充。它们有价值，但必须显式标注为补充或待核实，不能伪装成 Raw 支持的事实。

这不是否定 KB02 的方向。KB02 的事实提取、证据绑定和检查点恢复是深度写作必需的基础；本提案是在其上补齐“整篇组织、知识写作、质量审查和结构化渲染”。

## 2. 目标效果

KB03 的目标是让一篇 Raw 资料生成：

1. **一篇可读的 Source 深度整理笔记**：有知识定位、阅读主线、章节结构、解释、表格和关系图；
2. **一组可选的知识卡片建议**：继续遵守“一个 Wiki 尽量解决一个明确知识问题”的拆分原则；
3. **清晰的证据边界**：原文支持、重新组织、模型补充、待核实四类内容分开；
4. **可解释的覆盖报告**：关键事实被使用、合并或排除都有理由，不允许静默遗漏；
5. **可编辑的预览体验**：用户能修改标题、章节、正文、事实归属和待确认问题，确认后才写入正式 Wiki。

以用户提供的快消入门 Raw 为例，深度整理笔记应能形成：

```text
1. 快消品定义与商业特征
2. 四类主要产品品类
3. 商品流通链路三类供货路径
4. 供货层级与终端业态两个分析维度
5. 传统通路、现代通路与线上零售
6. 现代实体零售业态对照
7. 关键术语速查与易混点
8. 原文待核实清单与补充知识
```

输出应比 Raw 更容易学习，但不能通过虚构来源、无声合并口径或改写数值来换取流畅。

## 3. 非目标

本批不做以下内容：

- 不修改 Raw 正文，不自动补全 Raw 元数据；
- 不绕过草稿预览，不自动写入正式 Wiki；
- 不实现会议录音读取或会议自动标签；
- 不修改 Prompt Generator / Optimizer / PA01 范围；
- 不做全网自动核实，不给模型补充内容冒充已核实事实；
- 不重置 KB02 已用完的 40 次真实请求预算；
- 不把超长资料硬截断后假装完整整理；
- 不引入多 Provider、Agent 运行时、云同步或图数据库。

## 4. 用户体验方案

### 4.1 入口与模式

Raw 详情的“AI 整理”改为先显示模式选择：

| 模式 | 定位 | 适用 |
|---|---|---|
| 标准提取 | 现有 KB02 行为，偏事实和知识卡片 | 长资料、只需要入库结构时 |
| 深度整理 | 新增 KB03 行为，偏阅读和理解 | 文章、报告、入门学习资料 |

建议默认规则：

1. Raw 正文不超过 30,000 字符时，推荐并默认选择“深度整理”；
2. 超过 30,000 字符时默认“标准提取”，深度整理显示“本批暂不支持，后续扩展长文”；
3. 用户始终可以手动选择标准提取；
4. 旧 Raw 和旧草稿必须继续可读、可恢复、可编辑。

30,000 字符上限是用户确认后的 KB03 MVP 边界，目标是先把质量做稳定，而不是让长文在超时后失败。

### 4.2 深度整理阶段

```text
Raw
 → 结构扫描与语义事实提取
 → 整篇大纲规划
 → 深度笔记写作
 → 覆盖与证据质量检查
 → 人工预览与编辑
 → 显式确认写入
```

阶段说明：

1. **结构扫描**：识别标题、段落、列表、表格、明显标记和数值日期，保留原文结构线索；
2. **事实提取**：沿用已验证 locator，输出语义原子，保留主体、条件、时间、数值、单位和口径；
3. **大纲规划**：基于全部事实和原文结构，先设计笔记章节和每章要回答的知识问题；
4. **笔记写作**：按大纲生成段落、表格、路径图、术语表和边界提醒；
5. **质量检查**：校验证据、覆盖、数值、补充标注和来源元数据；
6. **人工预览**：展示整篇笔记、知识卡片、覆盖报告和待确认问题；
7. **确认写入**：深度笔记保存到 Source 页，用户选中的知识卡片另行创建或更新。

### 4.3 预览与编辑

预览页建议分为四个区域：

1. **深度整理笔记**：默认阅读视图，可切换到编辑视图；
2. **知识卡片建议**：沿用现有选择、编辑、合并、放弃和更新目标流程；
3. **证据与覆盖报告**：列出已使用、已排除、待确认的事实及原因；
4. **原始资料**：可并排或分栏查看 Raw，点击证据能定位原文。

编辑能力首版控制在必要范围：

1. 编辑章节标题和章节正文；
2. 编辑表格单元格、列表项和段落文本；
3. 删除或新增章节；
4. 调整章节顺序；
5. 修改待确认问题；
6. 标记某段为“原文支持 / 重新整理 / 模型补充 / 待核实”。

复杂富文本编辑器不在本批范围内。首版可以使用结构化表单加 Markdown 预览实现，重点是内容质量和证据边界。

### 4.4 保存语义

确认后：

1. **Source 页**新增 `## 深度整理笔记` 章节，保存渲染后的结构化笔记；
2. **Source 原有摘要、Key Takeaways、来源信息和涉及知识**继续保留；
3. **知识卡片**仍按用户选择创建或更新；
4. Raw 正文和校验值不变；
5. 未选中的卡片只出现在“本次未创建的建议”，不建立 Wikilink；
6. 模型补充内容在正式 Source 页中保持可见的“补充知识，未经原文支持”标识。

## 5. 结构化输出契约

产品规格要求 LLM 优先返回结构化 JSON，不允许直接返回自由 Markdown。KB03 使用结构化 block 表示笔记内容，再由服务端确定性渲染 Markdown。

### 5.2 block 类型

| type | 用途 | 约束 |
|---|---|---|
| `paragraph` | 解释、定义、总结 | 必须绑定 factIds 或声明补充 |
| `list` | 特征、步骤、要点 | 每项可绑定证据 |
| `table` | 品类、业态、术语对照 | 行级绑定证据和角色 |
| `path_diagram` | 流程、链路、关系示意 | 节点和边绑定证据 |
| `callout` | 边界提醒、纠偏、待核实 | 必须说明来源边界 |

### 5.3 内容角色

| role | 含义 | 渲染要求 |
|---|---|---|
| `source_supported` | 原文明确支持 | 显示证据引用 |
| `reorganized` | 对原文重新组织，不新增事实 | 显示来源证据，可合并多条 |
| `supplementary` | 原文没有，模型补充 | 明确标为“补充知识，未经原文支持” |
| `needs_verification` | 原文说法存疑或缺少口径 | 显示待核实原因 |

规则：

1. `supplementary` 不得进入 `source_facts`；
2. `source_supported` 必须绑定有效证据；
3. `needs_verification` 应进入待确认问题或覆盖报告；
4. 同一 block 不允许混合角色，混合内容必须拆分；
5. 重新组织不能改变主体、时间、数值、单位和条件。

## 6. 服务端流水线设计

### 6.1 语义事实增强

KB03 的深度模式在现有 facts 契约上增加可选语义字段：

```json
{
  "id": "f-c1-1",
  "text": "大卖场面积通常超过6000平方米。",
  "subject": "大卖场",
  "predicate": "面积参考",
  "value": "6000",
  "unit": "平方米",
  "qualifier": "原文描述，未提供统计时点",
  "locatorIds": ["c1-l001"]
}
```

字段要求：

1. `text` 仍是完整人读陈述；
2. 语义字段用于覆盖检查和数值校验，不替代证据；
3. 原文没有的维度必须为空或写入待确认，不得补齐；
4. 否定、条件、时间、口径和单位不得丢失；
5. 未知字段严格拒绝。

### 6.2 大纲规划

大纲规划器输入：

1. 已验证事实和问题；
2. Raw 结构线索；
3. 有限的 locator 上下文；
4. 来源元数据；
5. 目标笔记长度和章节上限。

大纲输出：

1. 笔记定位；
2. 章节标题；
3. 每章回答的知识问题；
4. 章节 fact/question 归属；
5. 明确排除项和排除理由；
6. 建议的知识卡片主题。

硬性要求：

1. 每个已验证事实必须被 `included` 或 `excluded` 之一；
2. 排除必须给理由；
3. 不允许为了页面数量硬拆；
4. 不允许生成“完整知识大全”式无边界章节；
5. 章节标题去重；
6. 所有 fact/question ID 有效且唯一归属。

### 6.3 笔记写作

写作器输入：

1. 已验证大纲；
2. 事实及证据引文；
3. 原文结构线索；
4. 允许的 block 类型；
5. 补充知识策略。

写作器任务：

1. 写出连贯解释；
2. 将适合对比的内容转成表格；
3. 将链路内容转成路径图；
4. 生成术语速查和易混点；
5. 把原文口径不稳定的内容放入待核实；
6. 把模型补充单独标记。

首版补充知识策略建议为“允许但受限”：

1. 只允许解释通用概念、常用分析维度或术语；
2. 不得补充具体公司数据、日期、数值、行业排名或预测；
3. 每篇笔记补充 block 数量建议不超过总 block 的 20%；
4. 补充内容必须集中在明确标注的段落或章节；
5. 用户可以在预览中删除。

### 6.4 质量检查

质量检查分为确定性和模型辅助两层。

确定性检查：

1. JSON schema 严格校验；
2. 所有 ID 存在且有效；
3. `source_supported` 和 `reorganized` 必须绑定证据；
4. 引文位置仍与 Raw SHA 对应；
5. 每个 fact 被包含或明确排除；
6. 数值、日期、单位与事实层一致；
7. 补充内容没有进入事实层；
8. 章节标题唯一，block 数量和输出大小有界；
9. 不允许自由 Markdown 绕过结构契约。

模型辅助检查：

1. 是否有明显主题遗漏；
2. 是否存在章节重复；
3. 是否把补充写成事实；
4. 是否存在表格或图形误表达；
5. 是否有更容易理解的重组建议。

模型检查结果只作为草稿质量报告，不能替代确定性校验，也不能自动修改正文。

## 7. 存储与渲染设计

### 7.1 DraftRecord 扩展

新增可选字段：

```text
organized_note?: StudyNoteRecord
organize_mode?: 'standard' | 'deep'
quality_report?: NoteQualityReport
```

要求：

1. 字段可选，旧 DraftRecord 必须兼容；
2. checkpoint 版本升级为 `kb03-1`；
3. 标准 KB02 checkpoint 不允许被伪装成深度整理结果；
4. Raw ID、Raw SHA、规则版本、Provider 身份和模式必须绑定；
5. 深度整理失败时保留已完成阶段，不回退成标准成功；
6. 用户显式恢复时才继续外发。

### 7.2 Markdown 渲染

服务端根据 block 确定性渲染：

1. `paragraph` → 段落；
2. `list` → 列表；
3. `table` → Markdown 表格；
4. `path_diagram` → 代码块中的文本路径图；
5. `callout` → 引用块；
6. 证据 ID 转为可定位引用；
7. 补充内容统一加“补充知识”前缀；
8. 待核实内容统一加“待核实”前缀。

不允许模型直接输出整篇自由 Markdown 后原样入库。用户在预览中手动编辑后的正文可以保存，但必须记录人工编辑标记。

### 7.3 Source 页保存

Source 页正文结构：

```text
## 来源信息
## 摘要
## Key Takeaways
## 深度整理笔记
## 涉及概念 / 实体 / 业务流程 / 指标
## 待验证内容
## Raw 来源
```

深度笔记是 Source 页的一部分，不改变 Wiki frontmatter schema，不新增顶层页面类型。

部分完成只能显示“可恢复”，不得显示为待确认草稿。

## 9. 验收质量标准

### 9.1 固定样例

使用用户提供的快消行业入门 Raw 作为第一验收样例。核心必须覆盖：

1. 快消品定义、商业特征和原文提到的代表公司；
2. 四类主要子行业及二级品类；
3. 品牌商、经销商、分销商、终端和消费者角色；
4. 直供、经销、分销三类路径；
5. KA 的原文定义；
6. 传统渠道、线上零售、现代通路；
7. 大卖场、现购自运、折扣店、标准超市、小型超市、高端超市、便利店、品类专营店；
8. 各业态面积、SKU 数、收银台数量、营业时间、门店数量等原文参数；
9. 原文中疑似转录错误或缺失图的内容不得被静默修正；
10. 原文来源信息只能按实际证据描述，不得断言完整来源为微信公众号或宣称作者日期已知。

### 9.2 质量评分

| 维度 | 及格标准 |
|---|---|
| 信息覆盖 | 核心主题无静默遗漏，排除项有理由 |
| 事实准确 | 不改主体、数值、单位、条件和时间 |
| 结构清晰 | 有主线，章节服务知识问题 |
| 可读性 | 比 Raw 明显更容易理解，不是事实堆砌 |
| 关系解释 | 供货层级与终端业态等关键关系讲清 |
| 边界透明 | 原文、重整、补充、待核实分开 |
| 证据可用 | 关键内容能定位 Raw 原文 |
| 编辑体验 | 用户能理解和修改输出 |

每项 0–5 分。建议阈值：总分不低于 32/40，且“事实准确”和“边界透明”均不低于 4/5。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 写作更流畅但事实变差 | 事实层先于写作，写作 block 必须绑定证据，数值做确定性检查 |
| 模型补充内容越界 | 补充 role 独立、数量受限、禁止具体数据，用户可删除 |
| 单次写作超时 | MVP 限 30,000 字符，阶段可恢复，不取消既有超时预算 |
| 长文覆盖不足 | 超上限默认标准提取，深度长文后续单独扩批 |
| UI 复杂度上升 | 首版结构化表单加预览，不做复杂富文本编辑器 |
| 与 KB02 已知问题耦合 | 不掩盖旧 FAIL；深度流水线新增质量门禁，旧问题按原返修卡追踪 |

## 13. 用户已确认的决策

1. **默认模式**：30,000 字符内默认“深度整理”；超过后默认“标准提取”。
2. **模型补充**：允许少量标注清楚的通用补充知识，但不得补充具体公司数据、日期、数值、行业排名或预测。
3. **保存位置**：深度笔记保存到 Source 页 `## 深度整理笔记`。
4. **真实预算**：批准 KB03 独立最多 12 次真实 Provider 验收，失败和诊断均计数。
5. **开工时机**：等待 PA01 独立审查闭环后启动。2026-10-16 复核 PA01 独立续验已 PASS；但当前 `docs/status.md` 最上方为 KB02 R2 待独立审查，正式 KB03 施工仍需遵守当前批次门禁和用户最新指令。

## 14. 结论

KB03 应把工作台从“事实提取与卡片组装”提升为“证据约束下的深度知识整理”。核心不是让模型自由写 Markdown，而是新增结构化的整篇大纲、笔记 block、质量检查和确定性渲染，让输出既接近参考笔记的可读性，又保留 Raw→Wiki 的证据链和人工确认边界。

本文档的关键决策已由用户确认。PA01 独立续验已 PASS，但当前工作区还有 KB02 R2 待独立审查；待当前批次门禁允许且用户明确启动后，才冻结为正式 KB03 任务卡并开始施工。
