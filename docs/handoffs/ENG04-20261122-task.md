# ENG04 代码格式化与静态检查基线 任务卡

属于[工程整固路线图](../batches/ENG-HYGIENE-ROADMAP-20261122.md)第三批，依赖 ENG02 和 ENG03 PASS（需要干净工作区和体积守护）。目标：

- 引入 Prettier 和 ESLint，用一次纯格式化提交把过密的单行代码展开，并证明产品语义完全不变；
- 静态检查接入 CI；
- 产出大文件拆分方案，供后续批次决策。

## 评分与模式

需求明确度 0 / 模块耦合 2（几乎所有产品与测试文件）/ 变更风险 1（只改格式，但触及草稿、提交、存储等数据完整性核心文件，用语义等价脚本兜底）/ 历史失败 0 = **3，A 标准**。按 agent-router 当前规则选模型；验收者先审计划，重点审等价性证明方法；施工与验收为不同实例。

**施工期间冻结其他批次**：格式化会和任何并行改动大面积冲突。

## 当前基线

- 无 Prettier、ESLint 配置和依赖。
- `app/server/services` 的 `.ts/.tsx` 中有 1,434 行超过 200 字符：app 605、server 50、services 779。最长的 2,979 字符，在 `services/llm/knowledge-answers.ts`。
- 大于 40KB 的产品文件：
  - `services/wiki/drafts.ts` 81.5KB、`services/raw/pdf-cleanup.ts` 69.7KB、`services/wiki/knowledge-workflows.ts` 63.4KB；
  - `services/wiki/commits.ts` 58.2KB、`services/meeting/store.ts` 57.7KB、`services/llm/jobs.ts` 48.8KB；
  - `services/prompt-ai/service.ts` 45.8KB、`app/pages/RawPage.tsx` 约 65KB 等。
- `useState` 数量：RawPage 53、AutomationPage 39、WikiPage 38、WorkItemsPage 38。页面路由和 URL 参数为手写。
- Git 索引为 LF，部分文件工作区为 mixed 换行（如 `app/App.tsx`、`services/wiki/drafts.ts`）。
- 历史报告中引用了大量产品和测试文件的 SHA-256，格式化后这些指纹只对应历史提交，属正常情况。

## 必做

**F1 Prettier 配置。**

- 精确版本加入 `prettier` 开发依赖，新增 `.prettierrc.json`：单引号、分号、`printWidth` 120、`endOfLine: "lf"`，其余用默认值（以用户 D3 决定为准）。
- `.prettierignore` 排除：`docs/`、`workspace/`、`dist/`、`node_modules/`、`evals/`（录制与 gold 数据）、`rules/`、`tests/acceptance/`（历史验收脚本，报告按 SHA 引用）、`public/`、`THIRD_PARTY_LICENSES/`、`package-lock.json`。
- 格式化范围：`app/`、`server/`、`services/`、`scripts/`、`tests/` 根层与 `tests/support/`、根配置文件。
- 新增 `.editorconfig`（UTF-8 无 BOM、LF、末尾换行）。
- npm 脚本：`format`（写入）、`format:check`（只检查）。

**F2 一次性格式化提交与等价性证明。**

- 格式化单独成一个提交，只包含 `npm run format` 的输出，不夹带任何手工修改。配置和依赖放在前一个提交。
- 新增 `scripts/format-equivalence.ts`。对每个被格式化的 `.ts`/`.tsx` 文件：
  1. 用项目已有的 esbuild（tsx 依赖）分别转换格式化前后的内容，参数为 `loader` 按扩展名、`jsx: automatic`、`minify: true`；
  2. 比较两份输出的 SHA-256。

  输出逐文件结果和汇总。期望 100% 一致；不一致的逐个列出原因，经验收者认可才可接受。
- 下一个提交新增 `.git-blame-ignore-revs`，写入格式化提交的完整 SHA；在 `docs/testing.md` 说明 `git config blame.ignoreRevsFile .git-blame-ignore-revs`。

**F3 ESLint 基线。**

- 精确版本加入 `eslint`、`typescript-eslint`、`eslint-plugin-react-hooks`，使用扁平配置 `eslint.config.js`，范围同 F1。
- 规则分级：推荐规则中当前违规为 0 的设为 error；违规较多的设为 warn，并在报告中记录基线数量。不得整组关闭推荐规则；关闭单条规则须写原因。
- 加 npm 脚本 `lint`。
- 本批**不修复** lint 发现的问题，只登记到报告。其中 `react-hooks/rules-of-hooks` 等可能是真实缺陷的，单列并说明复现思路，交主 Agent 决定是否另开批次。

**F4 接入检查。** `npm run check` 依次为 typecheck → format:check → lint → guard → test → build；`.github/workflows/ci.yml` 同步加入 `format:check` 和 `lint`。

**F5 拆分与前端状态治理方案（只出方案）。** 新增 `docs/reports/ENG04-20261122-split-plan.md`，覆盖：

- 大于 40KB 或格式化后超过 800 行的文件：现有职责、建议的模块边界、对外接口保持方式、现有测试覆盖、按 agent-router 维度的暂定评分；
- 拆分顺序：数据完整性核心文件（drafts、commits、knowledge-workflows、meeting/store）建议按 B 模式；
- 前端：URL 状态与轻量路由、请求缓存和过期响应处理（替代各页手写的刷新世代、选择世代）、大页面拆成自定义 hook 或 reducer 的方案与风险。

## 验收项

- **ENG04-01** `npm run format:check` 通过。验收者在格式化提交的父提交上用同版本 Prettier 独立重跑 `npm run format`，得到的树与格式化提交的树哈希一致，证明没有夹带手工修改。
- **ENG04-02** `scripts/format-equivalence.ts` 对全部被格式化的 `.ts`/`.tsx` 文件输出 100% 一致，或每个例外都有原因并经认可。验收者至少抽查 3 个数据完整性核心文件，独立复算。
- **ENG04-03** 格式化后 `app/server/services` 中超过 200 字符的行数从 1,434 降到只剩无法断开的长字符串，报告给出前后数字和剩余明细。
- **ENG04-04** `npm run lint` 退出码 0；warn 基线数量已记录；没有整组关闭的推荐规则；疑似真实缺陷单列。
- **ENG04-05** 隔离环境下 Node 22：`npm run check` 通过，且 3 条 eval 回放（standard-extract、news-relevance、weekly-review）结果与格式化前一致。远端 Windows Node 22/24 CI 在推送的提交上通过。
- **ENG04-06** `.git-blame-ignore-revs` 含格式化提交的完整 SHA，`git blame` 用法已写入文档。
- **ENG04-07** 除格式化提交外，其余提交对 `app/`、`server/`、`services/` 的改动为 0；拆分方案覆盖基线所列文件并给出评分与顺序。
- **ENG04-08** 回归：验收者用 TEMP 数据根和非用户端口启动生产构建，打开首页、Raw、知识库、自动化、设置页，无控制台错误和页面错误。

## 交付命令与操作

`npm run format:check`、`npm run lint`、`node --import tsx scripts/format-equivalence.ts`、`npm run check`（隔离环境变量）、`npm run eval -- --chain ...`（三条回放）、行长统计脚本、远端 Actions 结果读取。
