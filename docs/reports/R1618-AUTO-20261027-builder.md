## 根因与最小方案（已审）

真实新链为 `runKnowledgePipeline` → `KnowledgeWirePlan` → `expandKnowledgePlan` → 持久化 `KnowledgePlan` → 组装 `ExtractOutcome` → `DraftStore.fromExtracted`。当前严格 `kb02-planning.schema.json` 禁止额外字段，只允许页面标题、类型、分类、factUnitIds、questionUnitIds；expand/project同样只保留这些属性。组装固定将标题作为one_line_definition，AI整理/推断为空；fromExtracted也未复制templateFields。故当前协议根本不能产生自动字段，legacy service或人工UI单独修改无法补齐。

1. 扩展现有同一次planning响应：可选 `templateFields`，只允许Concept/Business Process现有字段；每项 `{text, factUnitIds}`。模型依语义归位本页fact unit，text独立作为AI整理，AI机会明确分析建议。字段无依据、未知、歧义不能确定时省略或保留待确认，不补写事实，不用关键词路由。字段引用不改变原page事实/问题恰好归属一次的覆盖规则；相同事实允许在多个相关字段引用。
2. expand将字段unit引用完整展开成原factIds；project可逆映回unit引用，不依赖标题或数组位置。检查未知、跨页、类型不合法引用；原事实文本、原证据、Raw逐字不变。持久化plan保存 `{text,factIds}`，旧plan缺字段仍可读。Schema内容参与现有rulesVersion哈希；旧未完成checkpoint仍遵现有版本不兼容提示并保留，不静默升级；已完成旧草稿不被改写。
3. 组装时程序从原factIds解析locator/evidence，写 `templateFields[key].aiContent={text,factIds,evidenceIds}`；人工 `evidenceIds/humanText` 继续独立。fromExtracted复制新字段。Draft校验将factIds锚定humanReview原始records及当前页assignment，证据必须为这些事实的完整实际引用；移动相关事实会明确拒绝并保全原稿，重命名不改变引用。现有合并/切型/旧Wiki更新的非空字段保护继续生效。字段合法性复用共享validator及已有存储读写，不加框架。
4. 复用现有字段编辑控件、保存、审批失效、完整预览与正式新建：AI文本使用独立可编辑区，能删除AI项；渲染明确“AI整理/AI归位（待核对）”，AI机会为“分析建议”；AI来源引用绝不显示为“用户归位”，绝不写humanText。人工说明及用户选择来源仍保持原标签。无AI字段的旧草稿保持原表现。
